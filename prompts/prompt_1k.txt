The history of distributed computing is, in many ways, a history of learning to live with latency. Every attempt to make a group of separate machines behave like a single larger one eventually collides with the same stubborn fact: moving a byte from one processor to another across a wire is thousands of times more expensive than reading it from local memory. Algorithms that look elegant on a whiteboard, where communication is assumed to be free, tend to fall apart the moment they are deployed onto real hardware connected by real cables. The engineers who succeed are the ones who treat the network not as an afterthought but as the central design constraint around which everything else must bend.

Consider the problem of splitting a large neural network across two computers so that each holds half of the model's weights. There are two broadly different ways to cut the work. The first is to divide the model by layer, sending the first block of layers to one machine and the remaining block to the other. Under this arrangement, a request flows through the first machine, crosses the network exactly once, and finishes on the second machine. The handoff is small, just the intermediate activations, so the fabric between the two nodes carries very little traffic. The weakness is that the two machines never work on the same request at the same time; while one computes, the other waits, and the total speed for a single request is no better than a single machine would achieve on its own.

The second approach is to divide every layer down the middle, so that both machines participate in computing each layer together. In principle this halves the arithmetic each node must perform, which is exactly what you want when you are trying to make one request finish faster. The catch is that after each layer, the two halves must reconcile their partial results, exchanging and summing them before the next layer can begin. This reconciliation, often called an all-reduce, happens many times for every single token the model produces. If the network round trip is slow, the machines spend most of their time waiting for one another rather than computing, and the theoretical speedup evaporates into idle silicon.

This is why the choice of interconnect matters so much. On specialized clusters, the machines are joined by dedicated high-speed links with hardware support for remote memory access, allowing one node to read or write another node's memory almost as if it were local, bypassing the operating system entirely. On commodity hardware, by contrast, the machines usually talk over ordinary networking, where every message must traverse the operating system's networking stack, be copied several times, and wait its turn behind other traffic. The difference between these two worlds is not a small constant factor; it can be the difference between a design that scales gracefully and one that is strangled by its own coordination overhead.

There is a further subtlety that is easy to overlook. The raw bandwidth of a link, the number of bytes per second it can carry when fully saturated, is often far less important than its latency, the time it takes for a single small message to make the trip. Tensor-parallel workloads send an enormous number of tiny messages, and each one must complete before the computation can proceed. A link with generous bandwidth but poor latency will still perform badly, because the machines are gated by how quickly they can complete a round trip, not by how much data they could move in bulk. Optimizing such a system therefore means attacking latency directly: pinning threads so they do not migrate, polling for completion instead of sleeping and waking, and shaving microseconds off the path a message takes from one process to another.

None of this is merely academic. As models grow larger than any single affordable machine can hold, the pressure to spread them across several smaller machines only increases. The organizations that manage to do this well, extracting real speed from a handful of modest computers rather than one expensive giant, gain a genuine advantage. But the path there is narrow, and it runs directly through the unglamorous engineering of making separate machines cooperate without waiting on each other. The most important number in the whole system is often the one nobody advertises: the time it takes for two nodes to agree on a single sum.
