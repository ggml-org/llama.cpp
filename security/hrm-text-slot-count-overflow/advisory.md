# Heap out-of-bounds write in the HRM-Text model loader via wrapped slot-count validation

## Affected code

Verified at HEAD `29b52d398b294509746ec0a3f28948a3107c0213` (branch `master`, 2026-11-20).
File: `src/models/hrm-text.cpp`.
Functions: `llama_model_hrm_text::load_arch_hparams()` and `llama_model_hrm_text::load_arch_tensors()`.

- CWE: CWE-190 (Integer Overflow or Wraparound) leading to CWE-787 (out-of-bounds write)
- CVSS 3.1: 7.8 - `CVSS:3.1/AV:L/AC:L/PR:N/UI:R/S:U/C:H/I:H/A:H`

## Summary

The HRM-Text architecture computes an expanded "cache-slot count" from three uint32
metadata fields read directly from the GGUF file: `n_hrm_layers_per_stack`,
`n_hrm_h_cycles` and `n_hrm_l_cycles`. The consistency check that is supposed to
bind this product to the model's `block_count` computes the product in 64-bit
arithmetic, but a true product of `2^64 + r` wraps to `r` in `uint64_t` and is
therefore accepted as equal to `block_count = r`.

The tensor loader then walks the very same three fields using 32-bit `int`
arithmetic to compute `slot_base` and writes pointers into the `layers` vector,
which was sized to `block_count`. With the wrapped metadata, `slot_base` grows
far beyond the vector and the writes go past its end, corrupting adjacent heap
memory. Loading a crafted GGUF file therefore results in a heap buffer overflow
during model load, with the attacker controlling the number and content of the
out-of-bounds writes.

## Vulnerable code (verbatim from the tested HEAD)

In `load_arch_hparams()`:

```cpp
    const uint64_t n_slot = (uint64_t) hparams.n_hrm_layers_per_stack * hparams.n_hrm_h_cycles * (hparams.n_hrm_l_cycles + 1);
    if (hparams.n_hrm_layers_per_stack >= hparams.n_layer() || n_slot != hparams.n_layer()) {
```

The three operands are uint32_t; their true product can reach `(2^32)^3`, well
above 2^64. The single 64-bit accumulator wraps before the comparison, so any
factor triple whose product equals `block_count + k*2^64` passes the check.

In `load_arch_tensors()`:

```cpp
    const int lps = hparams.n_hrm_layers_per_stack;
    const int h_first = hparams.n_hrm_l_cycles * lps;
    for (int h = 0; h < (int) hparams.n_hrm_h_cycles; ++h) {
        for (int l = 0; l < (int) hparams.n_hrm_l_cycles + 1; ++l) {
            const int slot_base = (h * (hparams.n_hrm_l_cycles + 1) + l) * lps;
                    layers[slot_base + il] = layers[src_base + il];
                auto &    layer = layers[slot_base + il];
```

`layers` has `block_count` elements (allocated by `layers.resize(n_layer_all)`).
`slot_base` and `blk_base` are computed with 32-bit arithmetic from the same
untrusted fields, so when the wrapped metadata is accepted the index used for
`layers[...]` runs past the allocation.

## Trigger data

All values are attacker-controlled uint32 GGUF metadata:

| field | value |
|---|---|
| `n_hrm_layers_per_stack` | 6 |
| `n_hrm_h_cycles` | 1824726041 |
| `n_hrm_l_cycles` | 1684887087 |
| `block_count` (`n_layer`) | 32 |

True product `= 6 * 1824726041 * 1684887088 = 18446744073709551648 = 2^64 + 32`.
The 64-bit accumulator `n_slot` wraps to `32`, which equals `n_layer() == 32`
and satisfies `layers_per_stack (6) < n_layer (32)`, so `load_arch_hparams()`
accepts the model. The loop index `slot_base` in `load_arch_tensors()` is 32-bit;
at `h = 0, l = 5` it reaches `30` and the inner loop writes `layers[32..37]` into
a 32-element vector.

## Malicious GGUF proof-of-concept

A minimal, self-contained malicious GGUF file is provided at
`harness/poc/poc_malicious.gguf` (15 KB, generated by `harness/make_poc_gguf.py`).
It declares the `hrm_text` architecture with `block_count = 32`,
`hrm.layers_per_stack = 6`, `hrm.h_cycles = 1824726041` and
`hrm.l_cycles = 1684887087`, plus small F32 tensors for blocks 0..5 so the
loading loop reaches the alias pass where the overflow occurs. The file parses
cleanly with the upstream `gguf-py` reader (`GGUFReader`: 38 tensors, 13 metadata
fields). Loading this model is the real-world trigger.

## Reproduction on the real binary

The malicious GGUF was loaded with an ASAN build of the upstream `llama-completion`
binary compiled from the tested HEAD on linux-amd64:

```bash
llama-completion -m poc_malicious.gguf -p hi -n 1
```

Result (`harness/poc_real_binary_vuln.log`):

```
ERROR: AddressSanitizer: heap-buffer-overflow
WRITE of size 3288 at 0x53300001a300
  #0 llama_model_hrm_text::load_arch_tensors(llama_model_loader&)  src/models/hrm-text.cpp:73
  #1 llama_model_base::load_tensors(llama_model_loader&)           src/llama-model.cpp:1848
0x53300001a300 is located 0 bytes after a 105216-byte region
  allocated by std::vector<llama_layer>::resize at src/llama-model.cpp:1845
```

The 105216-byte region is the 32-element `layers` vector; the writes run past
its end because `slot_base` is computed with 32-bit arithmetic from the wrapped
metadata. With `harness/fix.patch` applied and the binary rebuilt, the same file
is rejected during `load_arch_hparams` with "cache-slot count ... does not match
block_count" and no sanitizer report (`harness/poc_real_binary_patched.log`).

## Reproduction (isolated harness)

A self-contained harness reproduces the exact arithmetic of both functions from
the tested HEAD (tensor-layer internals stubbed; the check expression and the
indexed write are copied verbatim). Build and run under AddressSanitizer:

```bash
cd harness/
bash build.sh
bash run.sh
```

`harness/harness.log` records the result:

- baseline (`6 2 1 24`, product = 24, no wrap): 3/3 runs pass the check and
  report `WRITE_OK` with no out-of-bounds access;
- payload (`6 1824726041 1684887087 32`): 3/3 runs pass the check
  (`n_slot == n_layer == 32`) and then fault with
  `AddressSanitizer: heap-buffer-overflow, WRITE of size 8, 0 bytes after 256-byte
  region`, with the crashing frame in the reproduced `load_arch_tensors` write
  loop.

The baseline/payload differential shows the overflow is caused solely by the
wrapped metadata, and the 3/3 repeat runs show it is deterministic.

## Impact

Loading an untrusted GGUF model file with an HRM-Text architecture can corrupt
heap memory via out-of-bounds pointer writes. The writes are attacker-guided in
count and position, making this a plausible code-execution primitive in a process
that loads user-supplied models.

## Suggested fix

A ready-to-apply patch is provided at `harness/fix.patch`. It validates the
product in `__uint128_t` (so the three uint32 factors cannot wrap) and rejects a
value that does not exactly equal `block_count`; it also computes every
`slot_base` used to index `layers` in 64-bit arithmetic with a bounds assertion.
With the patch applied, the payload metadata is rejected at load time while a
legitimate model is unaffected.
