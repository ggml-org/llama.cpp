What is going on (evidence, not narrative)

- All four bcs coredumps share one signature: RING_ESR=0x1 (instruction error), blitter parsing a second-level batch at a deterministic NEO address. Three processes died at the identical VA 0xd556a9db0004 with IPEHR=0xfffff000; the fourth at 0xd556a9be0018 on a COMPUTE_WALKER. That is the copy command list's buffer holding non-blitter content when the blitter got to it.
- Four of five resets logged state=0x29 = REGISTERED|PENDING_DISABLE|SUSPENDED (kernel bit defs). That state exists only while xe suspends an exec queue for an LR-mode preempt fence, which fires on userptr invalidation or BO eviction. "Timedout job" is the cleanup after GuC's reset notice, not a timer.
- NEO creates every VM in LR mode and binds each pageable host pointer as MAP_USERPTR per copy. Its staging path is skipped whenever the copy has a wait event; UR chains every memcpy with one (inOrder: 0 lists). Source pages are the mmap'd GGUF. tlb_inval_count is 13.0 million this boot.
- This host migrates and reclaims pages constantly (pgmigrate_success 36.9M, compact_stall 28302, pgsteal_kswapd 131M, 3 GB free). i915 pinned userptr pages and never suspended contexts. xe suspends compute and blitter on every invalidation. Only the blitter breaks; the compute queue survives the same traffic, hence 0/10 with the copy engine off.
- Open question, one instrumented run away: xe/GuC blitter suspend/resume on DG2 (a), or NEO reusing the copy list buffer while the blitter is parked (b).

Plan

- Part A: four bounded offline runs (tracepoints + NEO allocation/bind logs) to settle (a)/(b) and confirm the trigger.
- Part B: fork change, auto-set UR_L0_USE_COPY_ENGINE=0 when an Intel node is on xe (sysfs check before any SYCL call, explicit user value wins), unit test, docs.
- Part C: trigger removal with no code: --load-mode none puts the fit's host-resident experts into pinned SYCL_Host memory (loader mmap guard is the only thing preventing it today). Measured with copy engine on and off.
- Part D: research doc, README correction, upstream report drafted but not filed without your go.

Plan: make the A770 work on the xe KMD (root cause + fix ladder)

Context

Two sessions today established that llama.cpp SYCL on the Arc A770 fails on the xe kernel driver (silent stalls, bcs engine resets with device coredumps) and that UR_L0_USE_COPY_ENGINE=0 avoids it (0 failures in 10, decode neutral on real text). 
The mechanism was left as "UR/NEO/xe cross-list event defect, failing event unidentified". 
The user wants the defect understood and xe fixed properly, not just fenced with an env var.

Evidence re-read this session (all read-only; paths under ~/research-llama.cpp/sycl-oneapi-benchmarks-2026-09-29/raw/, kernel journal, /proc, debugfs, NEO 26.35.39758.10 and kernel xe sources):

1. All four bcs coredumps share one signature. RING_ESR=0x1 (instruction error),
   RING_INSTDONE=0xfffffff7, CURRENT_LRCA=0x694001, and the blitter parsing a
   second-level batch (not the job's batch_addr 0xd556a8c66f00): three dumps from
   three different processes at the identical GPU VA ACTHD=0xd556a9db0004 with
   IPEHR=0xfffff000; the fourth at 0xd556a9be0018 with IPEHR=0x72080025
   (COMPUTE_WALKER). NEO heap placement is deterministic, so this is one specific
   recycled allocation: the copy immediate command list's command buffer, whose contents at
   execution time were not blitter commands.
2. The queue was mid-suspend in 4 of 5 resets. state=0x29 in the kernel log =
   REGISTERED|PENDING_DISABLE|SUSPENDED (xe_guc_submit.c bit definitions), which is
   exactly the state left by __guc_exec_queue_process_msg_suspend ->
   set_exec_queue_suspended(); disable_scheduling(). Suspends come only from LR-mode
   preempt fences (xe_preempt_fence.c: enable_signaling -> q->ops->suspend(q)), which
   fire on userptr invalidation (xe_userptr.c, dma_resv_wait_timeout on the VM
   resv) and BO eviction, then preempt_rebind_work_func rebinds and resumes. The
   "Timedout job" line is the TDR cleanup triggered by the GuC reset notification, not a
   5 s timer (Timeout: 0 (ms) in every dump; LR queues have MAX_SCHEDULE_TIMEOUT).
3. Every expert upload is a userptr bind on an LR-mode VM. NEO creates all VMs with
   DRM_XE_VM_CREATE_FLAG_LR_MODE (ioctl_helper_xe.cpp:1339), binds are always
   IMMEDIATE (:2066), host pointers become DRM_XE_VM_BIND_OP_MAP_USERPTR (:1826).
   NEO's staging-buffer path (which would avoid userptr) is disabled whenever the copy has
   a wait event: isValidForStagingTransfer(info, numWaitEvents > 0)
   (cmdlist_hw_immediate.inl:788) and isValidForStaging(...) && !hasDependencies
   (staging_buffer_manager.cpp:429). The UR trace shows every
   zeCommandListAppendMemoryCopy carries NumEventsInWaitList 1 (both immediate lists
   are inOrder: 0, ordering by event chaining). Source pages are the mmap'd GGUF
   (/proc/<pid>/maps: r--s file mapping, RSS 20 GB). Live counter:
   debugfs gt0/stats tlb_inval_count = 13,044,100 in 7.4 h of uptime.
4. This host churns pages constantly. /proc/vmstat this boot: pgmigrate_success 36.9M, compact_stall 28302, pgsteal_kswapd 131M, allocstall_movable 8148; 3 GB
   free, 34 GB cache (mergerfs, Plex, ZFS ARC). Under i915, userptr pages are pinned while
   in use and contexts are never suspended for a rebind. Under xe every migration or
   reclaim inside a live userptr range suspends both the compute and the blitter queue.
5. The blitter is the only casualty. DG2 has no direct submission for BCS
   (hw_info_dg2.cpp:34-39 lists RCS/CCS only), so blitter work is KMD-submitted jobs
   whose batches jump into the copy command list. With UR_L0_USE_COPY_ENGINE=0 there is
   no BCS exec queue at all, and the identical suspend/resume traffic hits only the CCS,
   which survives it (0/10 failures, production healthy since 16:50).

Two candidate defects remain, both below the application:
- (a) xe/GuC on DG2 mishandles suspend/resume of the blitter context (state restored
  wrongly, parser resumes on stale/foreign batch contents), or
- (b) NEO releases/reuses the copy command list buffer while the blitter is still parked
  or suspended on it (the COMPUTE_WALKER dump reads like the buffer had been handed to
  the compute list).

One instrumented run separates them (X1 below). Either way the application cannot fix the
defect; it can (1) stop depending on the blitter on xe, and (2) remove the trigger, which
is the per-copy userptr import of pageable expert pages. (2) is also a performance lever
on both drivers: hundreds of VM_BIND/unbind ioctls and TLB invalidations per token.

Part C: fork change 2, remove the trigger (pinned host-resident experts)

Goal: host-resident MoE expert weights that the scheduler streams every token
(ggml-backend.cpp:2376-2470, copy_experts) should live in pinned SYCL host memory
(ggml_backend_sycl_host_buffer_type, sycl::malloc_host) instead of pageable mmap'd
file pages, so the L0 memcpy source is a known USM allocation: no per-copy userptr
VM_BIND, no MMU-notifier exposure, no per-copy TLB invalidation. Expected to help on
both drivers; measured, not assumed.

How placement works today (verified in source):
    - --fit writes tensor_buft_overrides for expert tensors with
    ggml_backend_cpu_buffer_type() (common/fit.cpp:900, 955, 996, 1371, 1431);
    it aborts if the user passed any -ot (fit.cpp:807), so -ot exps=SYCL_Host is not
    a route.
    - The loader treats the plain CPU buft as a sentinel and runs
    select_weight_buft(buft_list_cpu) (src/llama-model-loader.cpp:1253-1255); that list
    is ACCEL, then the first device's host buft SYCL_Host, then CPU extra bufts, then CPU
    (src/llama-model.cpp:1147-1206, host buft added unless --no-host).
    - The only thing that turns SYCL_Host back into CPU_Mapped is the mmap guard at
    llama-model-loader.cpp:1282-1290. With mmap off the tensor is read from the file
    straight into sycl::malloc_host memory (loader:1688-1690; ggml-sycl.cpp:1778-1795).
    straight into sycl::malloc_host memory (loader:1688-1690; ggml-sycl.cpp:1778-1795).
    - SYCL_Host is still a host buffer for the scheduler (ggml-sycl.cpp:8140-8147,
    ggml-cpu.cpp:492), so copy_experts keeps running, now from pinned memory.

Options in order of preference:
    1. CLI only (X4): --load-mode none in the unit (LLAMA_EXTRA_ARGS) and in the bench
    flags. No code. If X4 is clean with the copy engine on and decode is not worse, this is
    the production fix for the trigger and gets documented in docs/backend/SYCL.md and the
    research doc. Side effects to state: every CPU-placed weight moves to SYCL_Host (not
    just experts; CPU_REPACK is bypassed on the normal fit path), RAM becomes an owned
    copy, load is a file read instead of page-cache sharing.
    2. Small code change (only if the user wants mmap kept for non-expert weights): make
    the guard at llama-model-loader.cpp:1282-1290 keep the host buft for tensors matched
    by an override that came from the fit (or behind a new --fit-pinned-experts flag,
    default off), loading them by copy from the mmap (loader:1653-1684 already handles
    cur->data != nullptr with ggml_backend_tensor_set). Keep the pinned-size caps in
    ggml-sycl.cpp:1827-1839 in mind; a tensor larger than the pinned limit silently falls
    back to CPU, so log the buffer type per tensor when the flag is on.
    3. If pinned placement fails on this host (malloc_host of ~10 GB refused), fall back to
    registering the mmap'd expert ranges once
    (sycl::ext::oneapi::experimental::prepare_for_device_copy) to remove the per-copy
    bind churn; MMU exposure remains, so this is a perf-only fallback.

Caveat to carry into the write-up: system-memory BOs bound to an LR VM are still
evictable by the xe shrinker under memory pressure, which also suspends queues; pinned
memory removes the userptr path but not every suspend on a host this loaded. Part B stays
the safety net.
