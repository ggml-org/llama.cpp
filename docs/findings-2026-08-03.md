# A. Confirmed baseline bugs in tessera

## A1. TESSERA_PAGED_ATTN was correctness-broken even for f16  [FIXED on main]

`set_input_tessera_page_map` (src/llama-kv-cache.cpp) built the page map by
walking only the current ubatch's spans (from `slot_info.idxs` via
`tessera_kv_block_table::make_page_map`). All historical logical positions
were left at their UINT32_MAX initialization, so during decode the paged
kernel attended to garbage cells and the model emitted repetitive junk
within ~3 tokens. The path only looked "fine" if you never checked the
output tokens; it did not crash.

Reproduce on baseline: `TESSERA_PAGED_ATTN=1 llama-cli -kvu ...` produces
repetitive garbage.

Fix: the `build_tessera_full_page_map` helper that inverts v_cells. Landed
on main via wave 1 (commit 25f5479a9). Source: memopt-pipeline-w1/best.md.

## A2. The v_trans mismatch (paged kernel + cache layout)  [FIXED on main]

The tessera paged-attn kernel reads V in row-major (non-transposed) layout
only. But the KV cache stores V transposed when flash_attn is off
(`v_trans = !flash_attn`). With `-fa off` (the w1/w3 test methodology and
the server default), the kernel read transposed V bytes as garbage. This
broke paged on EVERY model, not just SWA ones:
- qwen2.5-0.5B (no SWA): 1% -> 100% after fix
- gemma-4-12B: 1% -> 1% (separate issue, see A3)
- Verified with `-fa on` (v_trans=false) on qwen: paged already matched
  flash 100% BEFORE any code change, proving v_trans was the differentiator.

Fix: wave 4 (commit 0055a29c1) - force v_trans=false when paged is active,
plus a SWA page-map filter. Source: memopt-pipeline-w4/best.md.

## A3. Hybrid-iswa V-layout inference ambiguity (gemma SWA layers)  [FIXED on main]

`ggml_tessera_paged_attn` inferred whether V is stored transposed from the
tensor shapes: `v_trans = (v->ne[0] == k->ne[2])`. For gemma SWA layers the
V head dimension (256) equals the padded KV arena size (256), so the check
was ambiguous and the op wrongly selected the transposed-V access pattern
while the cache stores V non-transposed. It then read V at wrong offsets
and produced multilingual garbage from decode step 1 onward. The base
cache (head_dim 512 != 256) and qwen (head_dim 128 != 256) were unaffected.

Wave 4's gating masked this in production but the gemma paged path stayed
broken until wave 5. Root cause was NOT in the cache data (the data was
verified correct) - it was in the op's self-inflicted layout detection.

Fix: wave 5 (commit 10222c950) - thread v_trans as an explicit caller-
supplied parameter to `ggml_tessera_paged_attn`. The caller
(src/llama-graph.cpp build_attn) reads the authoritative cache layout via
`mctx_cur->is_v_trans()`. Shape inference removed. Source:
memopt-pipeline-w5/best.md.

## A4. Metal supports_op for TESSERA_PAGED_ATTN too narrow

Metal's `supports_op` for the paged op only accepted F32/F16 K/V, so any
quantized-KV paged op silently fell back to the CPU kernel. Source:
memopt-pipeline-w1/best.md. May be partially addressed by wave 1's q8_0
path; verify current state before relying on quantized-KV paged on Metal.

## A5. llama-bench had no -kvu flag

The paged path was unreachable from the standard evaluator regardless of
`TESSERA_PAGED_ATTN=1`. Fixed by wave 1 (commit 25f5479a9 added -kvu).
Source: memopt-pipeline-w1/best.md.

## A6. ops.cpp transitive-include quirk

`block_q8_0`/`QK8_0` are only visible in
`ggml/src/ggml-cpu/ops.cpp` if `GGML_COMMON_DECL_CPP` is defined BEFORE the
first include of `ggml-common.h`. Defining `GGML_COMMON_IMPL_C` is NOT
sufficient (it activates only the tables block, not the struct decls).
Source: memopt-pipeline-w1/best.md. Relevant to anyone extending the
paged-attn CPU kernel to new quant types.

## A7. imatrix: per-channel max_abs / abs_sums / fourth_sums collected but unused on the GGUF path

The imatrix producer (tools/imatrix/imatrix.cpp) collects and stores four
moments + max_abs per tensor (sums, abs_sums, fourth_sums, max_abs, counts
- see common/imatrix-loader.h). The tessera-side GGUF consumer
(tools/quantize/tessera/tessera-imatrix.cpp) uses only sums/counts and
reconstructs regime stats (kurtosis, eff_rank) from the per-channel mean-
squared-activation vector. The carefully-collected abs_sums, fourth_sums,
and max_abs are largely dead weight on the GGUF path.

This is a discovered bug, not a design choice. The single cheapest quality
win from the imatrix study: wire per-channel max_abs into the regime
router (ts_regime_compute_descriptor) and the DartQuant/CHAMP-Q expert
profiles so the regime classifier stops routing on a global kurtosis
scalar with no info on WHICH channels carry the outliers.

Source: imatrix-study/study.md sections 1, 2 (Q3).

## A8. dflash.cpp TODO is stale (DSpark Gemma4 works)

src/models/dflash.cpp:42 says: "TODO: only Qwen3-style backbones are

Source: orchestrator codebase survey, 2026-08-02.

# B. Build / tooling issues

## B1. WIP stash baselines omit untracked server sources

A `git stash create` baseline captures only tracked files. The tessera WIP
has 6 untracked server sources (`tools/server/server-admission.{cpp,h}`,
`server-metrics.{cpp,h}`, `server-prefill-policy.{cpp,h}`) referenced by
the committed `tools/server/CMakeLists.txt`. A baseline built from a bare
stash will fail to build `server-context`, `llama-server`, and
`test-server-prompt-cache` until those files are copied in.

This affected wave 1's baseline (53752d7) and any future worktree that
branches off a stash-create without including the untracked WIP. The wave
3/4 baselines on main (45fec5098 onwards) include the files.

Source: memopt-pipeline-w1/best.md.

## B2. Server --help / --version crashes on a build with the otel_sample_rate field missing

`tools/server/server-context.cpp:1630` reads `params_base.otel_sample_rate`
but the field was missing from `common_params` in `common/common.h`. The
server binary threw a `length_error` in argument parsing and crashed on
`--help` / `--version`. Fixed during pre-flight by adding
`float otel_sample_rate = 1.0f;` to common_params (included in the
baseline that became 53752d7).

Source: orchestrator pre-flight, 2026-08-02.

# C. Non-reproductions (claims that did not hold up)

## C1. LLAMA_KV_LAZY_CLEAR (wave 2 s2) does not reproduce

Wave 2 reported s2 ("skip the eager ggml_backend_buffer_clear on KV init
when LLAMA_KV_LAZY_CLEAR=1") as a -1.94% peak RSS win (-176 MiB on
gemma-4-12B Q5_K_M at pp512/n32) and shipped it on the w2 review branch.

On the cleaner wave-3 baseline (S1 + s2 both compiled in), it does NOT
reproduce:
  - lazy clear OFF: 8,300,724,224 B (~8.30 GB)  <- real floor
  - lazy clear ON:  8,891,383,808 B (~8.89 GB)  <- a +0.59 GB REGRESSION

Within run-to-run noise (~40-50 MB spread on the floor itself). Left OFF
by default. The wave 2 "win" was a measurement-order artifact.

Lesson: re-measure any memory claim against a clean baseline before
promoting it. Source: memopt-pipeline-w3/PREFLIGHT.md,
memopt-pipeline-w4/PREFLIGHT.md.

## C2. MoE pipeline "WILL produce artifact in 67 min" did not hold

The MoE-track agent reported the Qwen3.6-35B-A3B quantize pipeline was
running in the background (pid 89237) and would produce
/tmp/qwen35moe-awq-unified.gguf in ~67 min. Pid 89237 died at 435/753
tensors (`blk.23.attn_output.weight`) with no artifact produced. The
pipeline writes the entire output at the END via a single
gguf_write_to_file, so a death at 435/753 loses everything.

Diagnostic was lost (stderr went to nohup /dev/null). Most likely cause:
RAM contention - other agents (this session AND external ZCode sessions
on the same repo) were concurrently active on a 16 GB machine. No jetsam
event in the system log; ggml allocation asserts exit the process
directly without a kernel kill.

Lesson: background-run claims need immediate verification, not relay.
Retries must (a) run without concurrent inference work, (b) capture
stderr to a real file, (c) use --quantize-db so GA progress persists
across deaths.

Source: orchestrator monitoring, 2026-08-03.

## C3. orchestrator line-1256 mmap claim was wrong

When dispatching the imatrix study, the orchestrator claimed line 1256 of
tools/imatrix/imatrix.cpp (`no_alloc = false`) proved the producer eagerly
allocates the model. The imatrix-study agent caught the misread: line 1256
is the SAVE path (a small ggml context for writing outgoing stats),
NOT the model load. Whether common_init_from_params mmap's the model is
open and requires a runtime RSS measurement.

Lesson: do not infer from grep + line number; read the surrounding code.
Source: imatrix-study/study.md.

# D. Open / unresolved

## D1. v_trans=true kernel branch is only test-reachable

Wave 4's gating (`!mctx_cur->is_v_trans()` in src/llama-graph.cpp)
restricts the paged op to non-transposed V in production. The v_trans=true
branch of the Metal/CPU kernels is currently only exercised by
test-backend-ops. If that gating is ever relaxed (e.g. to let flash-on
paths use paged), the v_trans=true kernels need an independent correctness
audit on a real transposed cache.

Source: memopt-pipeline-w5/best.md.

# E. Process notes for future alphaevolve runs

## E1. The 16 GB Apple Silicon ceiling is the binding constraint

This machine cannot run multiple heavy inference workloads concurrently.
A single pp2048 llama-bench on the 12B OOMs; the 35B MoE (11.9 GB on disk)
loads but cannot run inference at all within 16 GB. Implications:
- run at most ONE llama-quantize / llama-bench / llama-server at a time
- the MoE quantize pipeline survives because of streaming weight load
  (commit 02ac74294), but only if nothing else competes for RAM
- multi-agent parallelism does NOT parallelize when the bottleneck is
  RAM: agents serialize at the eval step and contend for the ceiling

## E2. Concurrent ZCode sessions are invisible but real

This repo was being worked on by at least one other ZCode session during
this alphaevolve run. Evidence: 11+ scratch/agent-* and tessera/* branches
(dflash-gemma4 extraction, arg-cpp dedup, spec-calib API, tests, etc.)
plus 8 worktrees/agent-e-rebase-* directories appeared, none created by
this session. The tessera/auto-mtp-fix branch that this session deleted
early on reappeared later, almost certainly re-created by another session.

Any "run alone" guarantee is only as good as "alone among MY agents".
Future runs should check `git worktree list` and `ps aux | grep llama`
before assuming the machine is quiet.

## E3. Claims need verification, not relay

Three cases this session where an agent's claim was relayed and turned out
wrong or overstated: the MoE "WILL produce in 67 min" (C2), the wave-2 s2
-1.94% (C1), and the line-1256 mmap evidence (C3). In all three the
underlying work was valuable, but the orchestrator (me) should have
verified the specific claim before reporting it as fact. Verification is
cheap; re-measurement is the discipline.
