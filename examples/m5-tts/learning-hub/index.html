三条并行的线索

① 系统：端到端流水线

文本 → conditioning 序列 → backbone → 16-book depth 链 → codec → PCM。理解数据形状与单位，是所有优化的前提。

② 框架：llama.cpp 提供了什么

GGUF 模型加载、ggml 计算图与后端调度、llama_batch / llama_decode、KV cache 管理、量化。M5 是在这些原语上"借壳"运行的自定义模型。

③ 方法：性能工程

测量 → 分解 → 建模 → 假设 → 同轮 A/B → 质量门禁 → 记录（包括负结果）。这才是能带走的东西。

④ 专题：音色与情感

离散音频 token 如何承载说话人身份；零样本克隆的两条机制；为什么 caption 控制情感是弱训练槽。

口径约定 本文所有 RTF = 端到端生成耗时 ÷ 生成音频时长（越小越好）。不同章节的数据来自不同长度的测试句与不同设备热状态， 跨章节的绝对数字不可直接比较；每个结论都标注了它的对照实验。测试约定：同轮交替 A/B、固定种子/文本/音色、 质量门禁 = codes 确定性 + ASR 转写 + 音频统计族（RMS / 过零率 / 峰值）+ 必要时人耳试听。

01

认识被优化的对象：一帧音频是怎么来的

先把数据形状和计算图钉死，否则后面所有"优化"都是猜。

本章目标
  • 能画出 M5-TTS 的三阶段流水线，并说出每个张量的形状与单位
  • 理解 conditioning 序列为什么是"示范"，而不只是"条件"
  • 知道 llama.cpp 在这个工程里被复用了哪些原语、又绕开了哪些

1.1 三级火箭：backbone → depth → codec

把一段文本交给 M5，引擎先按标点切成若干段（每段 ≤80 字，总长 ≤2000 字），每段单独做一次 prefill：由控制标记、参考文本、目标文本、以及参考音频的 codec codes 拼成若干行 512 维 embedding， 一次性喂给 backbone。之后进入逐帧循环：backbone 走一步得到 hidden；depth 链用 15 次串行 decode 采出 16 个 code；codec 把攒够的若干帧解码成 PCM；next_hidden 再反馈给 backbone 开启下一帧。

与文本 LLM 的类比 prefill ↔ 读 prompt；逐帧 decode ↔ 逐 token decode；KV cache ↔ backbone 的上下文状态； sampler ↔ top-k 10 + 温度 0.9 + Gumbel-style 噪声采样；EOS ↔ 16 个 code 全 0（且前 6 帧禁止 EOS）。 不同点：LLM 一步采样 1 个 token，M5 一"步"要串行采 16 个 book，而且每个 book 的输入依赖上一个 book 的采样结果。

1.2 conditioning：把"示范"写进 prompt

// m5_engine.cpp:1392 condition() —— 实际渲染路径
<|caption_begin|>{caption}<|caption_end|><|accent_begin|><|accent_end|>
<|speaker_start|>None<|speaker_end|><|lang_begin|>Chinese<|lang_end|>
{voice.reference_text}{input_text}

// prefix 行布局（segment() :1101）
[ 控制标记 + 参考文本 token ][ 本段文本 token ][ 参考音频 codes 行 ]
   每行 = text_emb[id]              每行 = Σ_j audio_emb[code + 1 + j*2051]

注意 voice.reference_text 与 input_text 之间没有分隔符，参考文本在前。 参考音频 codes 的每一行是 16 个 codebook embedding 的逐元素求和（row = code + 1 + book*2051， +1 因为 0 是 EOS）。换句话说：模型在 prompt 里同时看到了"这句话该说什么"和"用谁的声音、什么韵律说过一遍类似的话"。 这就是 in-context learning 式的音色条件，不是把说话人向量注入到某一层。

1.3 llama.cpp 在这个工程里的角色

backbone.cpp 用 llama_model_load_from_file() 载入 GGUF，检查 n_embd == 512， 用 llama_context_default_params() 设 embeddings=true、type_k/type_v=F32、 n_ctx=2048（depth 子进程 256），然后构造一个不带 token 字段的 llama_batch： 只填 embd（512 维浮点行）、pos、seq_id 和 logits（只请求最后一行）。 llama_decode() 之后用 llama_get_embeddings_ith(ctx, -1) 取回最后一层 hidden。

工程约束 Snapdragon HTP 的 /dev/adsprpc-smd 对普通 App uid 返回 EACCES，只有 shell 域进程能用 DSP。 所以服务端形态（adb shell 启动的 m5-server）能跑 HTP，而 Android App 形态只能退到 native CPU。 这也是为什么 backbone/depth 被拆成常驻子进程：HTP 上下文初始化昂贵，且需要隔离崩溃域。

1.4 depth 链：16 个 book 为什么必须一个一个来

// m5_depth_heads.h: chain() 的骨架
proj(book0, hidden)  → logits[2051] → sample(T=0.9, top-k=10, noise=-log u) → code[0]
proj(projection, hidden) → projected_hidden
for book = 1..15:
    rows = (book==1) ? [projected_hidden, transform(code[0])] : [transform(code[book-1])]
    decoded = depth_decode(rows)          // 一次 llama_decode 调用，HTP 提交
    proj(book, decoded) → sample → code[book]     // 下一步的输入依赖这一步的采样结果
next_hidden = Σ_book audio_embedding[book][code[book]]   // 反馈给下一帧

权重布局（m5_depth_heads.h: layout()）：projection 块 16×2051×512 floats ≈ 67 MB（f32），projected 块 512×512， audio 块再来 16×2051×512。每帧要对 book 投影矩阵做 16 次 GEMV， 流式读取权重正是后面 f16 / int8 量化的用武之地。采样是 Gumbel 技巧： 噪声 n = -log(1-u) 由 JavaRandom LCG 生成，取 argmax(prob / noise)； 它要求按 book 顺序消耗随机数，因此"预生成噪声并向量化"也受到位精确约束。

本章要点 一帧 = 1 次 backbone decode + 15 次 depth 提交 + 16 次投影/采样 + 一批 codec 解码。 串行依赖有三层：book 内链、帧间 next_hidden、以及采样器随机数顺序。优化前先问：我要动的是哪一层依赖？
02

先学会测量：RTF、分层埋点与质量门禁

大多数"优化失败"，其实是一开始就量错了。

本章目标
  • 知道 RTF 什么时候会骗人，并能用"固定成本 + 每帧成本"拆解它
  • 能搭出端到端 / 分项 / 微基准三层可观测性
  • 理解为什么 TTS 优化必须带质量门禁，以及门禁各自的盲区

2.1 RTF 的定义与三个陷阱

RTF = 生成耗时 ÷ 生成音频时长。小于 1 表示"比实时快"。它直观、便于对比，但有三个坑：

  1. 短句惩罚：模型有固定的 prefill / codec 预热 / 首批调度成本，音频越短摊不掉。实测 7 字句 RTF 0.918，19 字 0.837，24 字 0.742——同一份代码，只因为句子长度不同。
  2. 热漂移：连续压测让 SoC 升温，同一代码 RTF 从 0.75 慢慢漂到 0.87、0.91。跨轮绝对值不可比，必须同轮交替 A/B（A→B→A→B）。
  3. 口径不一致：CLI 单次进程 vs server 常驻进程、wav 全量 vs pcm 流式、是否包含首次 codec prime，都会改变分子。
可迁移的做法 拿到一条耗时曲线，先做线性拟合：T(N) = 固定开销 + 每单位成本 × N。 截距指向冷启动 / prefill / 图初始化，斜率指向真正的逐 token（逐帧）热路径。 优化截距只对短请求有意义，优化斜率才对长请求有意义——两者 often 需要完全不同的手段。

这里有个值得记住的设计细节：HTTP chunked 响应在第一个分块发出时就已经把 headers 定稿， 而合成统计要等整段结束才知道，所以流式响应天生无法把最终统计放在响应头里。 本项目为此加了 /metrics：服务端留存最近 64 次请求的 JSON 明细与分位数， 并提供 Prometheus 文本格式；控制台在合成完成后拉取一次，用 last.id 认领本次记录， 把 ≈ 估算值替换为服务端权威值。

2.3 质量门禁：为什么"codes 不一样"不等于"错了"

自回归生成是混沌系统：任何 1-ulp 的数值扰动都可能让采样落在另一个 token 上，之后轨迹完全分叉。 因此门禁不是"逐位一致"，而是分层：

① 数值正确性

看首帧。改动若引入系统性误差，第 0 帧就会翻。heads int8 首帧 0/16 翻转，说明量化无偏。

② 轨迹分叉可解释

帧 2 起通过 next_hidden 反馈放大到 ~90% 翻转——这是"同分布另一条采样轨迹"，同级于换随机种子。

③ 语义与听感

ASR 两句全对、RMS/过零率/峰值同族、模式内确定性 0% 翻转。必要时再加人耳试听。

④ 什么时候必须否决

backbone Q4_0 让音频短 16%（语速变快），ASR 依然全对——只有耳朵能抓到韵律漂移，最终保持 Q8。

03

成本模型：把 15 步串行看透

本章是整门课的核心——用一个微基准，把"能不能批量化"变成可计算、可证伪的问题。

本章目标
  • 会用 bench 数据拟合"固定提交成本 + 每行成本"，并算出理论加速上限
  • 理解为什么理论 2.1× 拿不到，以及六条压缩路径各自是怎么被排除的
  • 能把这里的推理迁移到 LLM 的投机解码 / Jacobi decoding 讨论

3.1 一次调用多少钱

depth_batch_bench.cpp 在 HTP0 上把 28 行输入拆成四种形状，各跑多轮取中位数：

形状总耗时含义
1 × 28（一次提交 28 行）26.7 ms批量的理想情况
14 × 2（14 次提交，每次 2 行）42.6 ms接近现状
28 × 1（28 次提交，每次 1 行）60.4 ms最碎的提交方式
1 × 2（单次 2 行基线）3.07 ms校准固定开销

用 T = F·调用次数 + R·行数 拟合，得到 F ≈ 1.25 ms/次提交，R ≈ 0.91 ms/行。 于是现状（一帧 15 次调用、16 行）≈ 15×1.25 + 16×0.91 ≈ 33 ms； 理想批量（1 次调用、16 行）≈ 1.25 + 16×0.91 ≈ 16 ms。 理论上限约 2.1×，对应整句 RTF 从 ~0.75 降到 ~0.55。这是值得认真追查的收益。

3.3 六条"精确压缩"路径，逐条被实验关掉

路径想法证伪证据结论
① 哑输入批量把 15 步合成 1 次，transform 行先用零占位M5_ZERO_TRANSFORM=1 让 codes 翻转 99.6%（首帧 15/15 全翻），音频 70→500 帧发散不终止❌ transform 行承载语义与 EOS 决策
② 投机草稿用上一帧 codes 做草稿，一次批量 verify帧间 codes 匹配率仅 0~1.5%（lag 1-5 都是），近似随机❌ codec codes 没有时间局部性
③ Jacobi 迭代并行猜 15 步再迭代收敛依赖沿 15 步链传播，收敛需 O(15) 轮❌ 比串行更差（分析排除）
④ 跨帧批量把多帧一起 decodenext_hidden 反馈给下一帧 backbone 输入❌ 帧间被自回归锁死
⑤ 后端算子融合减少 op 数量OPFUSION 0 vs 1 只差 5%（44.6 vs 42.5 ms），深度图太小❌ 已见底
⑥ 减少 IPC 往返--depth-chain：16 次 pipe 往返 → 1 次逐位一致（宿主 200 组随机输入 0 mismatch）；但实测 depth 4.15 vs 4.08 s（-1.5%）⚠ 正确但没收益：瓶颈不是往返
最重要的结论 理论上限 ≠ 可达上限。2.1× 的收益是真的，但拿不到它的原因是模型语义：15 步串行是训练出来的依赖结构，不是实现偷懒。 任何"把 15 次合成 1 次"的精确方案都必须先回答：transform 行里的 code 依赖怎么办？ 到目前为止的答案是：要么训练一个小草稿模型做预测（学习型），要么重训 depth 头支持并行出多 book。
04

优化复盘（上）：让数据搬运变便宜

量化、算子融合、编译期验证——这一组优化的共同敌人是"字节数"和"扫描次数"。

本章目标
  • 会用"权重流量 × 带宽"估算 GEMV 耗时，并据此判断量化能省多少
  • 理解 f16 宏事故、int8 混沌分叉、Q4 被耳朵否决这三件事各自的方法论含义
  • 区分钟算式优化与提交开销型优化

4.1 f16：一个"优化了但根本没编译进去"的故事

depth heads 每帧要做 16 次 512×2051 的 GEMV，权重是流式读取的。 最初的 f16 内核守卫写成了 GCC 风格宏 __ARM_FEATURE_FP16，而 NDK clang 19 实际定义的是 __ARM_FEATURE_FP16_VECTOR_ARITHMETIC / __ARM_FEATURE_FP16_FML。 结果宏从未匹配、f16 是死代码，而构建日志与一次 objdump 检查都误报"已生效"，于是留下"RTF 持平"的假象。

修复动作有两步：改对宏名，并在 CMakeLists 里全局加 -march=armv8.2-a+fp16+fp16fml； 验证方式是反汇编数指令（确认 128 条 fmlal 真的出现），再做同种子交替 A/B： 每帧 57.3 → 48.3 ms（-16%），5/5 测试句 RTF 改善 11~13%。

教训 编译期优化必须以产物为准（反汇编 / 符号 / 计时），不能以构建日志或"代码写对了"为准。 宏名要按实际编译器的特性宏写；跨平台 SIMD 路径尤其容易静默回退到标量实现。

4.2 heads int8：带宽减半，heads 快 2.5 倍

埋点显示 heads 每帧约 13.4 ms，而每帧要流过约 34 MB f16 权重（投影 + projected 块）， 折算带宽约 2.5 GB/s —— 这是典型的内存带宽瓶颈，算力几乎没参与。 于是做 per-row 对称量化：每行 512 个 float 求 max|w|，scale = max/127， 存成 int8 + 一个 float scale；GEMV 用 NEON 把 int8 解包后以 f32 累加，最后乘回 scale。 注意 只量化权重、输入仍保持 f32，避免激活量化的误差叠加。

量化还带来一个必须讲清楚的现象：codes 从第 2 帧起翻转 ~90%。别急着判死刑——见下面这张图。

4.3 什么时候量化必须被否决：backbone Q4_0

用 host 端 llama-quantize --allow-requantize 把 backbone 从 Q8_0(32.4 MB) 压到 Q4_0(17.1 MB)， 同轮交替 A/B 的数据很漂亮：backbone_s 0.632 → 0.495（-21%），depth 也因 DDR 竞争减少快了 15%， 两版 ASR 全对。但音频时长从 5.90 s 缩到 4.94 s（-16%，语速变快）——这是韵律漂移。 人工试听后决定保持 Q8_0：TTS 的自然度优先于这部分 RTF，且 backbone 只占墙钟约 14%。

方法论 ASR 检查的是"说了什么"，韵律检查的是"怎么说"。生成式任务的指标天然偏向内容， 凡是改动会影响采样分布的优化，都要有感知层验收（这里是人耳；图像任务里是视觉检查/感知指标）。 同时要算清收益占比：为了 14% 的环节去牺牲全局听感，通常不划算。

4.4 codec：三步量化 + 一次"反直觉"的算子融合

动作效果原理
CT → MatMul 改写、权重动态 int8模型 362 → 141 MB；codec 7.49 → 4.68 s（115 帧句）让算子落到 ORT 的量化快速路径
融合 Snake 激活为自定义算子RTF 0.898 → 0.837snake(x)=x+c·sin(αx)² 原图是 Mul→Sin→Pow→Mul→Add 五遍全量扫描，Sin 单核占 codec ~14%；融合后用 9 次多项式正弦单遍算完（误差 ~2e-6）
ORT 线程数 A/B2/3/4 线程 = 3.56 / 2.84 / 3.20 s → 3 最优核数继续增加会因调度/缓存竞争变慢
反直觉但已实测 把 Snake 链用图级多项式展开成 13+ 个标准算子反而更慢——每多一个算子就多一次全张量读写。 "算子数量少"不总等于快，内存扫描次数才是这里的成本。融合成单个自定义算子才能同时省扫描和 Sin。

另外两个死胡同也值得记：尾部 ConvTranspose 保留 fp32 只有 12.78 vs 12.75 dB 的无差别收益； 对 QK^T / AV 这类"激活 × 激活"的 MatMul 做量化会掉 1.3 dB（Softmax 敏感），因此动态量化时必须把 17 个这样的节点排除。

4.5 小结：怎么判断"该不该量化"

  1. 先测流量与耗时是否成比例（改权重的位宽做 A/B），确认是带宽瓶颈；
  2. 若是，优先量化流式读取的大权重块，且尽量只量化权重、保留激活精度；
  3. 用首帧一致性 + ASR + 感知验收三层门禁，别用逐位 codes 当标准；
  4. 算清该环节在总墙钟的占比，收益天花板 = 占比 × 提速比例；
  5. 如果环节被流水线重叠隐藏（codec），现在优化它不会反映在端到端 RTF 上——等主瓶颈降下来再做。

5.3 分块策略与"固定开销"的第二次出现

codec 是带递归状态的 ONNX 会话，按 chunk 批量解码。chunk 越小首包越早，但每次 ORT Run 有固定开销； 于是按请求类型分策略：

完整 wav：first=4, chunk=16

反正听不到过程，大 batch 把 ONNX 调用从 18 次降到 5 次。

启动预热

服务启动后跑一句丢弃模式的短合成，把 backbone prefill、depth 图、ORT kernel 全部热身；首请求首包 0.58 → 0.29 s。启动多花 ~1.5 s，一次付清。

WavWriter 三模式

文件 / 内存 / 丢弃。wav 响应直接在内存拼 RIFF 头，pcm 流式只计数不落盘——去掉白做的磁盘 I/O。

规律 "更小的块 = 更低延迟"只在固定开销小时成立。任何带会话初始化、图提交、DMA 的调用都要先量它的固定成本， 再决定分块粒度。这与 §3.1 的 F 是同一个概念，只是发生在 codec 层。

5.4 prefill 前缀 KV 缓存：一个协议级优化

同一音色的每次请求，prefix 的前半段（控制标记 + caption + 参考文本）完全一样，只有目标文本与参考 codes 后面的部分不同。 既然 backbone 是标准 llama.cpp context，就可以保留共享段的 KV，只重算新增部分。

还有两个同类的"别重复做"：Codec::restore_prime 按参考 codes 的最后 8 帧缓存 codec 递归状态， 同音色第二次请求起跳过一次 primer ORT Run；voices.json 按 mtime 缓存，避免每请求重读解析。

6.3 性能问题诊断模板（可直接抄）

  1. 锁定口径：固定输入、固定种子、设备冷却到同一状态；记录 RTF、墙钟、首包、帧数。
  2. 画泳道：把 prefill / 主 decode / 辅助解码 / I/O 画在时间线上，标出哪些重叠、哪些串行。
  3. 拟合：T(N) = 截距 + 斜率 × N；截距归冷启动，斜率归热路径。
  4. 分类瓶颈：改字节数（带宽）、改调用次数（提交）、改并发（竞争）、改输入长度（依赖），一次只动一个变量。
  5. 算天花板：该环节占墙钟百分之几 × 最多提速几倍。占比 <10% 的环节先别碰。
  6. 做 A/B：同轮交替、至少两轮；把负结果和复活条件一起写进文档。
  7. 过门禁：数值正确性 → 生成分布 → 语义/感知 → 必要时人耳/人眼。
  8. 固化：把赢下来的配置写进部署脚本与监控，防止下次重启静默回退。

7.2 Serena 的诞生：五步，零梯度

7.3 为什么一堆整数 codes 能带音色

神经音频 codec（如 RVQ / 多码本量化）把波形压成 [帧, 码本层] 的整数序列。 M5 与 Qwen3-TTS-12Hz 都是 12.5 Hz、16 层码本 的设定；Qwen3-TTS 技术报告明确： 第一层码本偏向语义内容，后续层逐层补充声学细节（音色、气息、环境、韵律）， 因此容量足够用轻量级因果 ConvNet 直接重建波形，不需要单独抽取说话人向量，也不需要扩散模型。

离散化带来的好处

说话人身份被编码成 token 序列后，语言模型可以像处理文本一样"读"它；于是音色变成了上下文，而不是某个需要注入的向量。

为什么必须带逐字转写

M5 的 prompt 里参考文本与 codes 是配套的：模型需要知道这段声音"说的是哪句话"，才能把音色与内容解耦，续写新文本时沿用前者、替换后者。

为什么 3-30 秒就够

零样本克隆不更新权重，只需要足够覆盖音素与韵律的上下文。本项目的 serena 参考约 65 帧（≈5.2 s），服务端上限 375 帧（30 s）。

情感也在这里

语气、语速、停顿同样留在 codes 里。所以"换一段带情绪的参考音频"比写 caption 更可靠（见 §7.7）。

7.4 零样本克隆的两条机制

机制做法优点局限本案例
Speaker embedding说话人编码器把参考音频压成固定维向量，注入 LM 的每一步实时、与文本无关、便于跨语言容易丢韵律细节；需要联合训练编码器Qwen3-TTS 的实时克隆路径；llama.cpp 里映射为 mtmd audio encoder
Text–speech pair / in-context把「参考文本 + 参考音频 codes」直接拼进 prompt，让模型续写更好地保留韵律；无需额外编码器占上下文长度；依赖 tokenizer 与训练格式M5 走这条：voices.json 里的 codes 作为前缀行
一句话回答"怎么学的" 没有梯度下降、没有 LoRA、没有微调。Qwen3-TTS 生成的一段音频被重新编码成 M5 自己词表里的离散 token， 作为 few-shot 示范放在 prompt 前面；M5 在自回归续写时把这段示范的统计特征（音色、语速、韵律）延续下去。 这在机器学习里叫 in-context learning（上下文学习），是推理时行为，不是训练时行为。

Qwen3-TTS 组件映射到 llama.cpp关键技巧
codec token扩展词表，追加 <|codec_0|>…<|codec_1023|>、<|codec_bos|>(2149)、<|codec_eos_token|>(2150)、<|codec_language_chinese|>(2055)把音频码字当成"词"，复用 embedding 表
text projection MLP折进 embedding 表减少一层计算，保持标准 decode 路径
codec_head输出张量比词表小，推理时 pad logits兼容 llama.cpp 的 logits 布局
speaker reference encodermtmd audio encoder复用多模态音频编码通路
backbone标准 libllama 自回归文本模型采样时 suppress_tokens 限制只出语义码本或 EOS
code_predictor / code2wavMTMD_GEN_PROCESS_TYPE_GEN_CODE / GEN_WAV把"预测其余 15 码本"和"解码波形"作为生成流水线的两个阶段
输入格式ChatML wrap + sum_row() 把文本 embedding 与 codec/speaker embedding 相加<|im_start|>assistant\n…<|im_end|>\n<|im_start|>assistant\n 后切片

把这张表和 §1.3 并排看，就是本教程最想让你体会的一点： llama.cpp 不关心你的 token 是字还是声音，它只关心 embedding 行、位置、序列 id 与计算图。 M5 与 Qwen3-TTS 两条实现，一个用 llama_batch.embd 直接注入，一个把音频码字扩进词表—— 两条不同的"借壳"路线，共享同一套 KV / 后端 / 量化基础设施。

7.7 情感控制为什么难：一个弱训练槽的案例

M5 的 conditioning 里有 <|caption_begin|>…<|caption_end|> 风格槽，但官方推理把它硬编码为空。 项目做过 7 档 caption（NONE / happy / sad / angry / gentle / 开心 / 悲伤）× 同句同种子，再用 4 个种子做噪声基线：

路径实测证据难度
caption 风格槽非空 caption 让时长 +0~42%，但 F0 / 能量变化落在种子噪声 ±8% 内 → 弱训练槽，无可靠语义情感控制接线低，效果不可靠
情感参考音频克隆codes 强烈迁移音色与韵律；录一段带目标情绪的参考即可低，但情感与音色绑定
DSP 后处理变调 / 变速 / EQ 可预测但机械低
训练侧（情感标注 CPT / SFT）模型卡注明改动 delimiter 需要继续预训练；稀疏训练导致 caption 无效高
实验纪律 种子带来的 F0 采样噪声本身就有 ±8%，所以任何 <10% 的"情感差异"都不可信—— 验证情感/风格效果必须多种子平均。这与 §2.1 的热漂移是同一类问题：先量噪声底，再谈信号。 相比之下 Qwen3-TTS 的 VoiceDesign 变体是专门用自然语言描述 + instruction 训练过的，属于"训练侧把槽位填满"。

8.2 思考题（先自己算，再展开）

Q1　为什么 7 字句 RTF 0.918 而 24 字句 0.742？这算优化成功吗？
不算。同一份代码，只是固定成本被摊薄。用 T(N)=截距+斜率×N 拟合：截距 ≈152 ms（prefill / 图初始化 / codec prime），斜率 ≈54.7 ms/帧（backbone 6.1 + depth 48.6，codec 被重叠）。 短句 23 帧摊 152 ms 固定开销，每帧多背 6.6 ms；长句 75 帧只多 2 ms。所以看性能必须固定输入长度，或同时报告截距与斜率。
Q2　depth 权重从 21 MB 降到 10.7 MB 只快 9%，你能推出什么？若改成 heads 权重减半呢？
若瓶颈是权重带宽，字节数减半应接近 2×；只有 9% 说明 depth 是提交开销 / 计算主导，继续降位量化没有意义。 而 heads 每帧流式读 34 MB、耗时 13.4 ms ≈ 2.5 GB/s，符合带宽特征；f16→int8 减半后 heads_s 0.94→0.38 s（2.5×），验证了判别。同一个动作效果相反，因为瓶颈类型不同。
Q3　流式首块从 2 帧改成 1 帧，为什么首包反而从 0.285 s 涨到 0.51 s？
少了一个 depth step 省下的时间，小于 codec 多一次 ORT Run 的固定开销 + 该会话的调度/状态准备成本。 这是 §3.1 的 F 在 codec 层的翻版：分块越碎，固定成本占比越高。结论是维持 2 帧，并把"1 帧更慢"写进代码注释防止后人重试。
Q4　int8 让 codes 翻转 90%，为什么还能上线？什么情况下你必须否决一个量化？
首帧 0/16 翻转证明没有系统性数值误差；之后是 next_hidden 反馈放大 1-ulp 差异造成的混沌分叉，等价换随机种子。 门禁看 ASR（语义）、音频统计族（分布）、模式内确定性 0% 翻转、人耳。 否决条件是感知层面的系统性偏移：backbone Q4 让音频短 16%、语速变快，ASR 全对也不行；或 codec 激活×激活量化掉 1.3 dB。
Q5　"用 Qwen3-TTS 的音色"这句话里，梯度更新发生在哪里？
迁移过程里一次都没有。Qwen3-TTS 自己的音色能力来自它预训练 / 后训练（含 speaker fine-tuning）时学到的映射； M5 只是把 Qwen 生成的一段音频重新编码成自己词表里的 codec codes，作为 prompt 前缀做 in-context learning。 运行时既不加载 Qwen 也不更新权重。真正"把槽位训练出来"的例子是 Qwen3-TTS 的 VoiceDesign（自然语言描述控制）， M5 的 caption 槽因训练稀疏而弱——这正是"槽位存在 ≠ 槽位可用"。
Q6　如果让你继续把 RTF 从 0.75 往下压，下一步做什么？
先算天花板：depth 占 83%，其余环节全砍掉也只有 ~17%。而六条精确压缩路径已被排除， 所以只剩改变依赖结构：训练学习型草稿（code[b]←(hidden, code[b-1])）做批量 verify，或重训 depth 头一次出多 book，理论 2.1×。 其次等 depth 降下来后，codec 的 3.0 s 才会从 overlap 里浮出成为新瓶颈，那时再做 codec 权重快路径 / int4 heads。 不建议先动被隐藏的 codec，也不建议为单用户场景改并发。
