三条并行的线索

① 系统：端到端流水线

② 框架：llama.cpp 提供了什么

③ 方法：性能工程

01

认识被优化的对象：一帧音频是怎么来的

先把数据形状和计算图钉死，否则后面所有"优化"都是猜。

本章目标
  • 能画出 M5-TTS 的三阶段流水线，并说出每个张量的形状与单位
  • 理解 conditioning 序列为什么是"示范"，而不只是"条件"
  • 知道 llama.cpp 在这个工程里被复用了哪些原语、又绕开了哪些

1.1 三级火箭：backbone → depth → codec

把一段文本交给 M5，引擎先按标点切成若干段（每段 ≤80 字，总长 ≤2000 字），每段单独做一次 prefill：由控制标记、参考文本、目标文本、以及参考音频的 codec codes 拼成若干行 512 维 embedding， 一次性喂给 backbone。之后进入逐帧循环：backbone 走一步得到 hidden；depth 链用 15 次串行 decode 采出 16 个 code；codec 把攒够的若干帧解码成 PCM；next_hidden 再反馈给 backbone 开启下一帧。

与文本 LLM 的类比 prefill ↔ 读 prompt；逐帧 decode ↔ 逐 token decode；KV cache ↔ backbone 的上下文状态； sampler ↔ top-k 10 + 温度 0.9 + Gumbel-style 噪声采样；EOS ↔ 16 个 code 全 0（且前 6 帧禁止 EOS）。 不同点：LLM 一步采样 1 个 token，M5 一"步"要串行采 16 个 book，而且每个 book 的输入依赖上一个 book 的采样结果。

注意 voice.reference_text 与 input_text 之间没有分隔符，参考文本在前。 参考音频 codes 的每一行是 16 个 codebook embedding 的逐元素求和（row = code + 1 + book*2051， +1 因为 0 是 EOS）。换句话说：模型在 prompt 里同时看到了"这句话该说什么"和"用谁的声音、什么韵律说过一遍类似的话"。 这就是 in-context learning 式的音色条件，不是把说话人向量注入到某一层。

1.3 llama.cpp 在这个工程里的角色

backbone.cpp 用 llama_model_load_from_file() 载入 GGUF，检查 n_embd == 512， 用 llama_context_default_params() 设 embeddings=true、type_k/type_v=F32、 n_ctx=2048（depth 子进程 256），然后构造一个不带 token 字段的 llama_batch： 只填 embd（512 维浮点行）、pos、seq_id 和 logits（只请求最后一行）。 llama_decode() 之后用 llama_get_embeddings_ith(ctx, -1) 取回最后一层 hidden。

工程约束 Snapdragon HTP 的 /dev/adsprpc-smd 对普通 App uid 返回 EACCES，只有 shell 域进程能用 DSP。 所以服务端形态（adb shell 启动的 m5-server）能跑 HTP，而 Android App 形态只能退到 native CPU。 这也是为什么 backbone/depth 被拆成常驻子进程：HTP 上下文初始化昂贵，且需要隔离崩溃域。

1.4 depth 链：16 个 book 为什么必须一个一个来

// m5_depth_heads.h: chain() 的骨架
proj(book0, hidden)  → logits[2051] → sample(T=0.9, top-k=10, noise=-log u) → code[0]
proj(projection, hidden) → projected_hidden
for book = 1..15:
    rows = (book==1) ? [projected_hidden, transform(code[0])] : [transform(code[book-1])]
    decoded = depth_decode(rows)          // 一次 llama_decode 调用，HTP 提交
    proj(book, decoded) → sample → code[book]     // 下一步的输入依赖这一步的采样结果
next_hidden = Σ_book audio_embedding[book][code[book]]   // 反馈给下一帧

权重布局（m5_depth_heads.h: layout()）：projection 块 16×2051×512 floats ≈ 67 MB（f32），projected 块 512×512， audio 块再来 16×2051×512。每帧要对 book 投影矩阵做 16 次 GEMV， 流式读取权重正是后面 f16 / int8 量化的用武之地。采样是 Gumbel 技巧： 噪声 n = -log(1-u) 由 JavaRandom LCG 生成，取 argmax(prob / noise)； 它要求按 book 顺序消耗随机数，因此"预生成噪声并向量化"也受到位精确约束。

本章要点 一帧 = 1 次 backbone decode + 15 次 depth 提交 + 16 次投影/采样 + 一批 codec 解码。 串行依赖有三层：book 内链、帧间 next_hidden、以及采样器随机数顺序。优化前先问：我要动的是哪一层依赖？
想看物理执行位置？ 本章讲的是逻辑数据流；哪些模块真正在 HTP0、哪些在 CPU、一帧要跨越多少次 pipe， 以及为什么 App 形态拿不到 NPU，统一放在 第 9 章 · NPU / CPU 边界。

先学会测量：RTF、分层埋点与质量门禁

大多数"优化失败"，其实是一开始就量错了。

本章目标
  • 知道 RTF 什么时候会骗人，并能用"固定成本 + 每帧成本"拆解它
  • 能搭出端到端 / 分项 / 微基准三层可观测性
  • 理解为什么 TTS 优化必须带质量门禁，以及门禁各自的盲区

2.1 RTF 的定义与三个陷阱

RTF = 生成耗时 ÷ 生成音频时长。小于 1 表示"比实时快"。它直观、便于对比，但有三个坑：

  1. 短句惩罚：模型有固定的 prefill / codec 预热 / 首批调度成本，音频越短摊不掉。实测 7 字句 RTF 0.918，19 字 0.837，24 字 0.742——同一份代码，只因为句子长度不同。
  2. 热漂移：连续压测让 SoC 升温，同一代码 RTF 从 0.75 慢慢漂到 0.87、0.91。跨轮绝对值不可比，必须同轮交替 A/B（A→B→A→B）。
  3. 口径不一致：CLI 单次进程 vs server 常驻进程、wav 全量 vs pcm 流式、是否包含首次 codec prime，都会改变分子。
可迁移的做法 拿到一条耗时曲线，先做线性拟合：T(N) = 固定开销 + 每单位成本 × N。 截距指向冷启动 / prefill / 图初始化，斜率指向真正的逐 token（逐帧）热路径。 优化截距只对短请求有意义，优化斜率才对长请求有意义——两者 often 需要完全不同的手段。

2.3 质量门禁：为什么"codes 不一样"不等于"错了"

自回归生成是混沌系统：任何 1-ulp 的数值扰动都可能让采样落在另一个 token 上，之后轨迹完全分叉。 因此门禁不是"逐位一致"，而是分层：

① 数值正确性

看首帧。改动若引入系统性误差，第 0 帧就会翻。heads int8 首帧 0/16 翻转，说明量化无偏。

② 轨迹分叉可解释

帧 2 起通过 next_hidden 反馈放大到 ~90% 翻转——这是"同分布另一条采样轨迹"，同级于换随机种子。

③ 语义与听感

ASR 两句全对、RMS/过零率/峰值同族、模式内确定性 0% 翻转。必要时再加人耳试听。

④ 什么时候必须否决

backbone Q4_0 让音频短 16%（语速变快），ASR 依然全对——只有耳朵能抓到韵律漂移，最终保持 Q8。

3.1 一次调用多少钱

depth_batch_bench.cpp 在 HTP0 上把 28 行输入拆成四种形状，各跑多轮取中位数：

形状总耗时含义
1 × 28（一次提交 28 行）26.7 ms批量的理想情况
14 × 2（14 次提交，每次 2 行）42.6 ms接近现状
28 × 1（28 次提交，每次 1 行）60.4 ms最碎的提交方式
1 × 2（单次 2 行基线）3.07 ms校准固定开销

用 T = F·调用次数 + R·行数 拟合，得到 F ≈ 1.25 ms/次提交，R ≈ 0.91 ms/行。 于是现状（一帧 15 次调用、16 行）≈ 15×1.25 + 16×0.91 ≈ 33 ms； 理想批量（1 次调用、16 行）≈ 1.25 + 16×0.91 ≈ 16 ms。 理论上限约 2.1×（只算 depth core 的提交开销）。但这个数字后来被两次修正： 算上 heads 投影后 depth 阶段天花板只有 1.78×，而且 codec 与 depth 并行， 单独提速会被 max() 吃掉；§14 又证明学习型草稿的 α 上界只有 0.18， 连这个 1.78× 都拿不到。详见 Ch 9。

3.3 六条"精确压缩"路径，逐条被实验关掉

路径想法证伪证据结论
① 哑输入批量把 15 步合成 1 次，transform 行先用零占位M5_ZERO_TRANSFORM=1 让 codes 翻转 99.6%（首帧 15/15 全翻），音频 70→500 帧发散不终止❌ transform 行承载语义与 EOS 决策
② 投机草稿用上一帧 codes 做草稿，一次批量 verify帧间 codes 匹配率仅 0~1.5%（lag 1-5 都是），近似随机❌ codec codes 没有时间局部性
③ Jacobi 迭代并行猜 15 步再迭代收敛依赖沿 15 步链传播，收敛需 O(15) 轮❌ 比串行更差（分析排除）
④ 跨帧批量把多帧一起 decodenext_hidden 反馈给下一帧 backbone 输入❌ 帧间被自回归锁死

最重要的结论 理论上限 ≠ 可达上限。2.1× 的收益是真的，但拿不到它的原因是模型语义：15 步串行是训练出来的依赖结构，不是实现偷懒。 任何"把 15 次合成 1 次"的精确方案都必须先回答：transform 行里的 code 依赖怎么办？ 曾经的答案是「训练一个小草稿模型做预测」，但 §14 用 960 帧官方 ONNX 轨迹把这条路也关掉了： 可预测性沿 15 步链结构性衰减，α 上界 ≈0.18 远低于盈亏平衡 0.72（Ch 9 / 图 9-2 就是草稿跨不过去的那段依赖）。 现在只剩重训 depth 头支持并行出多 book——那是改模型图、需要原始训练数据的另一个项目。

优化复盘（上）：让数据搬运变便宜

量化、算子融合、编译期验证——这一组优化的共同敌人是"字节数"和"扫描次数"。

本章目标
  • 会用"权重流量 × 带宽"估算 GEMV 耗时，并据此判断量化能省多少
  • 理解 f16 宏事故、int8 混沌分叉、Q4 被耳朵否决这三件事各自的方法论含义
  • 区分钟算式优化与提交开销型优化

4.1 f16：一个"优化了但根本没编译进去"的故事

depth heads 每帧要做 16 次 512×2051 的 GEMV，权重是流式读取的。 最初的 f16 内核守卫写成了 GCC 风格宏 __ARM_FEATURE_FP16，而 NDK clang 19 实际定义的是 __ARM_FEATURE_FP16_VECTOR_ARITHMETIC / __ARM_FEATURE_FP16_FML。 结果宏从未匹配、f16 是死代码，而构建日志与一次 objdump 检查都误报"已生效"，于是留下"RTF 持平"的假象。

修复动作有两步：改对宏名，并在 CMakeLists 里全局加 -march=armv8.2-a+fp16+fp16fml； 验证方式是反汇编数指令（确认 128 条 fmlal 真的出现），再做同种子交替 A/B： 每帧 57.3 → 48.3 ms（-16%），5/5 测试句 RTF 改善 11~13%。

教训 编译期优化必须以产物为准（反汇编 / 符号 / 计时），不能以构建日志或"代码写对了"为准。 宏名要按实际编译器的特性宏写；跨平台 SIMD 路径尤其容易静默回退到标量实现。

4.2 heads int8：带宽减半，heads 快 2.5 倍

埋点显示 heads 每帧约 13.4 ms，而每帧要流过约 34 MB f16 权重（投影 + projected 块）， 折算带宽约 2.5 GB/s —— 这是典型的内存带宽瓶颈，算力几乎没参与。 于是做 per-row 对称量化：每行 512 个 float 求 max|w|，scale = max/127， 存成 int8 + 一个 float scale；GEMV 用 NEON 把 int8 解包后以 f32 累加，最后乘回 scale。 注意 只量化权重、输入仍保持 f32，避免激活量化的误差叠加。

量化还带来一个必须讲清楚的现象：codes 从第 2 帧起翻转 ~90%。别急着判死刑——见下面这张图。

4.3 什么时候量化必须被否决：backbone Q4_0

用 host 端 llama-quantize --allow-requantize 把 backbone 从 Q8_0(32.4 MB) 压到 Q4_0(17.1 MB)， 同轮交替 A/B 的数据很漂亮：backbone_s 0.632 → 0.495（-21%），depth 也因 DDR 竞争减少快了 15%， 两版 ASR 全对。但音频时长从 5.90 s 缩到 4.94 s（-16%，语速变快）——这是韵律漂移。 人工试听后决定保持 Q8_0：TTS 的自然度优先于这部分 RTF，且 backbone 只占墙钟约 14%。

方法论 ASR 检查的是"说了什么"，韵律检查的是"怎么说"。生成式任务的指标天然偏向内容， 凡是改动会影响采样分布的优化，都要有感知层验收（这里是人耳；图像任务里是视觉检查/感知指标）。 同时要算清收益占比：为了 14% 的环节去牺牲全局听感，通常不划算。

4.5 小结：怎么判断"该不该量化"

  1. 先测流量与耗时是否成比例（改权重的位宽做 A/B），确认是带宽瓶颈；
  2. 若是，优先量化流式读取的大权重块，且尽量只量化权重、保留激活精度；
  3. 用首帧一致性 + ASR + 感知验收三层门禁，别用逐位 codes 当标准；
  4. 算清该环节在总墙钟的占比，收益天花板 = 占比 × 提速比例；
  5. 如果环节被流水线重叠隐藏（codec），现在优化它不会反映在端到端 RTF 上——等主瓶颈降下来再做。

7.2 Serena 的诞生：五步，零梯度

7.3 为什么一堆整数 codes 能带音色

神经音频 codec（如 RVQ / 多码本量化）把波形压成 [帧, 码本层] 的整数序列。 M5 与 Qwen3-TTS-12Hz 都是 12.5 Hz、16 层码本 的设定；Qwen3-TTS 技术报告明确： 第一层码本偏向语义内容，后续层逐层补充声学细节（音色、气息、环境、韵律）， 因此容量足够用轻量级因果 ConvNet 直接重建波形，不需要单独抽取说话人向量，也不需要扩散模型。

离散化带来的好处

说话人身份被编码成 token 序列后，语言模型可以像处理文本一样"读"它；于是音色变成了上下文，而不是某个需要注入的向量。

为什么必须带逐字转写

M5 的 prompt 里参考文本与 codes 是配套的：模型需要知道这段声音"说的是哪句话"，才能把音色与内容解耦，续写新文本时沿用前者、替换后者。

为什么 3-30 秒就够

零样本克隆不更新权重，只需要足够覆盖音素与韵律的上下文。本项目的 serena 参考约 65 帧（≈5.2 s），服务端上限 375 帧（30 s）。

情感也在这里

语气、语速、停顿同样留在 codes 里。所以"换一段带情绪的参考音频"比写 caption 更可靠（见 §7.7）。

8.2 思考题（先自己算，再展开）

Q1　为什么 7 字句 RTF 0.918 而 24 字句 0.742？这算优化成功吗？
不算。同一份代码，只是固定成本被摊薄。用 T(N)=截距+斜率×N 拟合：截距 ≈152 ms（prefill / 图初始化 / codec prime），斜率 ≈54.7 ms/帧（backbone 6.1 + depth 48.6，codec 被重叠）。 短句 23 帧摊 152 ms 固定开销，每帧多背 6.6 ms；长句 75 帧只多 2 ms。所以看性能必须固定输入长度，或同时报告截距与斜率。
Q2　depth 权重从 21 MB 降到 10.7 MB 只快 9%，你能推出什么？若改成 heads 权重减半呢？
若瓶颈是权重带宽，字节数减半应接近 2×；只有 9% 说明 depth 是提交开销 / 计算主导，继续降位量化没有意义。 而 heads 每帧流式读 34 MB、耗时 13.4 ms ≈ 2.5 GB/s，符合带宽特征；f16→int8 减半后 heads_s 0.94→0.38 s（2.5×），验证了判别。同一个动作效果相反，因为瓶颈类型不同。
Q3　流式首块从 2 帧改成 1 帧，为什么首包反而从 0.285 s 涨到 0.51 s？
少了一个 depth step 省下的时间，小于 codec 多一次 ORT Run 的固定开销 + 该会话的调度/状态准备成本。 这是 §3.1 的 F 在 codec 层的翻版：分块越碎，固定成本占比越高。结论是维持 2 帧，并把"1 帧更慢"写进代码注释防止后人重试。
Q4　int8 让 codes 翻转 90%，为什么还能上线？什么情况下你必须否决一个量化？
首帧 0/16 翻转证明没有系统性数值误差；之后是 next_hidden 反馈放大 1-ulp 差异造成的混沌分叉，等价换随机种子。 门禁看 ASR（语义）、音频统计族（分布）、模式内确定性 0% 翻转、人耳。 否决条件是感知层面的系统性偏移：backbone Q4 让音频短 16%、语速变快，ASR 全对也不行；或 codec 激活×激活量化掉 1.3 dB。
Q5　"用 Qwen3-TTS 的音色"这句话里，梯度更新发生在哪里？
迁移过程里一次都没有。Qwen3-TTS 自己的音色能力来自它预训练 / 后训练（含 speaker fine-tuning）时学到的映射； M5 只是把 Qwen 生成的一段音频重新编码成自己词表里的 codec codes，作为 prompt 前缀做 in-context learning。 运行时既不加载 Qwen 也不更新权重。真正"把槽位训练出来"的例子是 Qwen3-TTS 的 VoiceDesign（自然语言描述控制）， M5 的 caption 槽因训练稀疏而弱——这正是"槽位存在 ≠ 槽位可用"。
Q6　如果让你继续把 RTF 从 0.75 往下压，下一步做什么？
先别急着动任何模块——这道题在 2026-11-15 被三项实测改写了（Ch 9）。 ① 天花板不是 2.1×：算上 heads 后 depth 上限只有 1.78×，而且 codec 与 depth 并行， wall ≈ backbone + max(depth, codec) + prefill；只做草稿会被 codec 卡住。 ② 三条看似可行的路全部排除：单边旋钮与资源让渡（§13，48 次 A/B 无一快于默认）、 codec 单独优化（被 max 吃掉）、学习型草稿（§14，α_oracle ≈ 0.18 ≪ 0.72 盈亏平衡）。 ③ 所以不改模型图时稳态 RTF 0.725 已是极限；把精力转向首包、热漂移、功耗、音质， 或接受「重训非自回归 depth head」这个需要训练数据的另一个项目。 这题真正考的是：先看清依赖结构与并行结构，再判断某个优化能不能兑现。

9.1 计算归属全景

真正跑在 HTP0 上的只有两个 transformer：backbone（8 层 Q8_0，32 MB）与 depth core（5 层 Q4_0，10.7 MB），合计约 43 MB 权重常驻。 heads 投影、采样、噪声生成、codec 声码器、PCM 输出全在 CPU。

9.2 为什么这样切

① transformer 归 NPU

backbone / depth core 都是规则 GEMM，权重小（32 MB / 10.7 MB）可常驻 HTP，每层都能被 llama.cpp 的 ggml-hexagon 后端整图提交。HVX 向量单元擅长这个。

② heads 留 CPU

depth-weights.f32 是 202 MB 查表型权重，每步只取 1–2 行；CPU 侧 mmap + per-row int8 镜像（17 MB/帧流式读）+ NEON 更划算。带宽特征明显：int8 后 heads 快 2.5×。

③ codec 留 CPU

ONNX Runtime 图，含自写 m5::Snake 自定义算子，走 CPU EP（3 线程）。它不是 GGUF，也进不了 ggml-hexagon 的图。

④ 两个进程，一个 NPU

backbone-resident / depth-resident 是同一二进制的两个常驻子进程，角色由 argv 决定；各自一个 HTP 会话，分时复用同一 HTP0。拆开是为了 KV 隔离、分别调量化与 env。

9.3 一帧内的 15 次跨边界往返

引擎 ↔ stage 一行 FP32 512 维 = 2 KB。默认 --depth-pipe 下，每个 book 都要「CPU 构造 transform 行 → 送 HTP0 跑一步 depth core → 回 CPU 投影 2051 类 → 采样」，一帧 15 次。--depth-chain 能把整条链搬进 stage、一次往返，但实测打平；m5_ring 共享内存反而更慢——瓶颈从来不是 IPC 次数。

9.4 真实一帧：max() 天花板

2026-11-15 03:31 的实跑请求（Serena，87 帧）：墙钟 5.281 s、RTF 0.770、首包 0.561 s；分项 backbone 0.734 / depth 4.160 / codec 3.156 s，折合每帧 8.4 / 47.8 / 36.3 ms。

把结构变成判据 wall ≈ backbone + max(depth, codec) + prefill。两条分支一旦接近， 任何单边优化都会被 max() 吃掉：codec 变快而 depth 不变，墙钟一动不动； depth 变快到 codec 以下，codec 立刻变成新瓶颈。这比"哪个模块慢就优化哪个"的直觉重要得多。

9.6 两个容易误解的点

两个 HTP 会话 ≠ 两个 NPU

都是 HTP0，只是两个独立的 llama 上下文（各自 KV、各自量化）。它们分时复用同一物理 DSP。

App 形态拿不到 HTP

OS 对 app uid 封了 /dev/adsprpc-smd（EACCES），JNI 版只能全 CPU 跑（RTF ~0.79–0.90）。只有 shell 域启动的 m5-server 才能用 NPU——所以本章与 §13/§14 的 NPU 结论只适用于 server 形态。

Q7　既然 codec 有 25% 的空闲余量，为什么"让 codec 少干点活、把 CPU 让给 depth"没用？
因为 depth 的 47.8 ms 主体花在 HTP0 的 15 次提交（F≈1.25 ms/次 + R≈0.91 ms/行），不是 CPU 争抢。实测把 ORT 线程从 3 降到 2 会让 codec 慢 25%，而 depth_s 反而略升；chunk 从 4 加到 16 让 codec 快 7%，depth_s 几乎不动。 并发反压确实存在（关 overlap 后 depth 快 11.3%），但它是"codec 线程存在"的固定税，不是负载强度的函数；而 overlap 本身净赚 43.9%，这笔税必须付。

用 Profile 调查提速后的音质变化

Serena 用 Flash Attention 加速后，有个别字听起来像破音。先用同一文本、音色和种子复现，保留基线。听感是验收条件，RTF 只描述吞吐。

  1. 按 DSP OPBATCH 切分 trace，只比较相同形状的 decode。旧 profile 有 1,820 个 80 算子批次。按算子族汇总，三个矩阵乘法族合计约 1.64 ms/批，SET_ROWS、RoPE、Softmax 也占时间。用 DSP 批次计时和 host API 计时分别判断核内执行与端到端等待。
  2. 加中间对照来分离变量。FP32 普通注意力约 2.65 ms/decode，FP16 普通注意力约 2.60–2.65 ms，FP16 Flash 约 1.92 ms。用 FLASH_ATTN_EXT 的 HTP profile 确认真正走了 HVX。不同配置生成帧数会变化，因此用相同 decode 次数衡量提速。
  3. 按码本隔离生成和解码。分别保存基线与 Flash 生成的 codes，再对比两种 codec 下的 codes 哈希和 WAV。在本例中，同一 attention 配置跨 codec 的 codes 完全一致。四份 PCM16 均未到满幅，排除了 PCM16 满幅削顶。Flash 的后续 chunk 分别用 2、4、8 帧，输出 WAV 逐字节相同，可以降低对分块边界的怀疑。
  4. 用同 codes 的试听定位。如果 Flash 的 INT8 与 FP32 都在同一个字出现问题，优先查生成轨迹；如果只有 INT8 明显，优先查 codec。本轮人工试听把问题定位到「别着急」，同一组 Flash codes 的 INT8 版更明显，FP32 版有所缓解。优先检查 INT8 图的量化边界，同时保留 Flash 轨迹可能影响局部发音的判断。要评估动态导航，把数字、方向、路名和单位列为独立验收项。

固定同一组 Flash codes，把 codec 尾部三层（conv_28–30）连同量化边界恢复为 FP32。用户试听确认全 FP32 明显更好，尾部混合版与 INT8 接近。混合版仍实时，但首 PCM 从 430–446 ms 增至 502–565 ms，因此不采用。下一次应按上采样阶段做较粗的精度消融，先确定哪段值得细分。

同句对比时，用户认为生产版明显优于 Flash 的两种分阶段混合精度版。上游改变了 codes，恢复 codec 精度未找回原有听感。当前组合同时改变了 KV 精度和注意力实现，听感结果不能单独归因到 Flash kernel。后续保留 FP32 KV 和采样语义，先检查 codes 与 WAV 一致，再比较速度。

补测 FP16 KV 的普通注意力后，用户反馈没有破音，但韵律下降。随后保留 FP32 KV，尝试跳过 CPU 采样中概率为零的候选。两种种子的 codes 和 WAV 均与基线逐字节一致，但速度改善没有跨种子复现。这组实验说明，音质验收与性能验收需要分别通过。

继续按同形状批次拆分 KV 写入，K 与 V 的 SET_ROWS 均值约为 34 和 164 µs。另测只输出 depth 的末行 embedding，KV 写入保留两行。两个文本的 codes 和 WAV 均一致，但双轮主样本的 RTF 只从约 0.824 到 0.820。因此保存补丁作为实验，后续优先剖析 V 的散写。

把 FP32 V 的 128/256 个标量改为在 DSP 上按索引直接写入，V 写入时间约从 164 µs 降到 28 µs，两个测试文本的 codes 和 WAV 与基线一致。按权重与缓存名分组后，QK/AV 与 FFN 各约 0.7 ms/步；QKV 和 gate/up 已经融合。按算子名统计只能发现大类，按实际张量名才能决定下一处优化。

保持 FP32 KV 与普通注意力，把短序列 KV 的读取范围从 256 改为按 32 对齐，保留原 cache 容量和全部有效位置。两组 codes 和 WAV 逐字节一致，端到端减少约 10%。这是利用模型真实形状减少被掩蔽计算的例子。用单行 decode profile 归因，再用独立 A/B 验收墙钟。

转正：从实验开关变成编译期默认。实验阶段它只存在于一个隔离 runtime 目录里，靠部署脚本给 depth 子进程注入 M5_KV_PAD32=1 才生效，源码默认仍是 256。转正时把 get_n_kv() 的 pad 默认改为 32（M5_KV_PAD=256 可回退），并让 backbone 分支显式保留 256——因为它的 prefill prefix 会随整句增长，而且原实验只有 depth 用了 32，必须严格复现实验条件。V 直接散写同时转为默认（M5_HVX_DIRECT_V=0 关闭）。部署脚本不再需要特殊目录和 env 注入，并补上了原本缺失的 stage 库推送。12 次交替 A/B：默认 3.775 s / RTF 0.710，pad 256 为 4.163 s / 0.783，关 direct-V 为 3.894 s / 0.732；12 次 codes 与 WAV 的哈希全部相同，backbone 耗时无退化。

提速成功后，瓶颈结构会改变。转正前 depth 4.53 s、codec 3.62 s，之间有 25% 余量；转正后 depth 2.853 s、codec 2.820 s，只差 1.15%。流水线的墙钟是 backbone + max(depth, codec) + 固定开销，于是单独把 depth 再降 27%（Flash 级）只剩 -0.9%，哪怕把 depth 降到零也只是 -0.9%；单独把 codec 降 20% 是 0%。只有两者一起降 20% 才有约 -15%。这正是第 3 章「先看天花板再动手」的实战版：一个成功的优化会把旧的余量吃光，让此前划算的方向突然变得不划算。后续 P0 归因实验（§17）确认：即使 KV 保持 FP32，融合 kernel 也会改变 codes 与帧数，单帧只快 6.9% 而整句墙钟反而 +5.1%，这条线判死。方法沉淀见下一章。

盲听复核。三条文本各出两份音频，a/b 顺序打乱，映射表在反馈前不揭晓。用户指出第 3 组（车站播报）的 3a 有点差；揭晓后 3a 正是融合 kernel 版，3b 是基线。这是独立于 codes/WAV 哈希、ASR 和 RTF 的人耳证据：KV 精度没变，只换 attention 实现也能被听出来。按等价性分层的第 ③ 层，不通过即否决。样本量小（3 组、仅 1 组被明确指出），所以结论是「不进入生产」，不是「所有文本都能听出差异」。

性能分析方法论：从分项到判死

前面十章讲的是「这个模型怎么加速」。这一章把过程中反复用到的判断方式抽出来：它们不依赖 M5-TTS，换一个推理引擎、换一块 NPU 也成立。核心只有一句——先算清楚这个优化能兑现多少，再决定要不要动手。

11.1 为什么先建模型

分项统计（backbone_s / depth_s / codec_s）本身不是模型，把它们的结构关系写出来才是。本项目的两条分支并行重叠，所以墙钟是 backbone + max(depth, codec) + 固定开销，不是三者相加。用残差检验：不同配置下减出来的固定项都约 0.197 s，说明模型抓住了结构。有了它，动刀之前就能算出「codec 降 20% 值多少」——在 §13 的答案是 0，在 §16 的答案仍是 0。省下的是一整轮无用的量化实验。

11.2 十条速查判据

  1. 先写可证伪的墙钟模型，用它算可兑现收益，不要用单项耗时当目标。
  2. 区分「组件变快」与「端到端变快」；max() 结构下优化非瓶颈分支收益为 0。
  3. 每次成功优化后重算余量、重排优先级：KV32 把 25% 余量吃到 1.15%，旧结论立即失效。
  4. 同轮正逆序交替 A/B，固定文本与 seed、取中位数；判据是 elapsed_s。热漂移能让同代码 RTF 从 0.75 变 0.91。
  5. RTF 只在输出不变时可用。分母 audio_s 会随生成轨迹变化，必须同时看墙钟、每帧成本、输出长度。
  6. 等价性分层：① codes/WAV 逐字节；② ASR + 音频统计；③ 多文本人耳盲听。heads int8 与 B/Q4 都证明「指标全对 ≠ 听感通过」。
  7. 归因实验一次只改一个变量（KV 精度 × kernel 实现），并用 profile 数算子证明改动真的生效，别靠 env 名猜。
  8. 算子形状比墙钟推测更接近机制：SOFT_MAX 256:32:8:1 直接解释融合 kernel 为何只剩 7%。
  9. 负结果写清机制与复活条件：α 上界 0.18、反压是固定税、可预测性沿链衰减、kernel 改变轨迹。
  10. 先做便宜的判死实验，再投入训练或改图。960 帧离线数据判死草稿，16 次合成判死 Flash 线。

11.3 四个反复出现的陷阱

分母会变

flash-f32 的 RTF 从 0.700 降到 0.666，看似快 5%；实际帧数 69→76、音频长 10.5%、墙钟 +5.1%。只看 RTF 会得到完全相反的结论。

只看单边指标

--threads 3、chunk (2,4)、OPPOLL=1 都是按「codec 单独耗时」「首包最短」定的。§13 用端到端墙钟重扫 48 次，没有任何配置快于默认。

把近似当等价

codes 分叉、帧数漂移时，两条轨迹已经不是同一个任务；此时比速度没有意义，先过门禁再谈性能。

沿用旧基线

「Flash 是最大杠杆（-17%）」在 KV32 之前成立；转正后它只剩 ~0.9%。每条结论都要带上它的基线。

冷 / 热口径混用

CLI 每次都是新进程，codec prime 缓存必然空；常驻 server 同音色第二次起就命中，首包差约 0.08 s。之前所有分项实验用 CLI，报的都是冷启动数。延迟必须标明是「重启后首次」还是「稳态」。

11.4 把负结果变成资产

§12–§14、§17 四条线全部判死，但留下的是可复用的机制：α 上界、固定税、可预测性衰减、kernel 轨迹漂移。写清楚「为什么不行」和「什么条件下复活」，比记录「试过没收益」有价值得多——它让下一个人不必重跑一遍，也让自己不会在换基线后重复投入。

11.5 案例：把 0.398 s 首包拆开

稳态 RTF 被 max() 锁死（§16），但首包由固定项主导，是另一本账。扫 --first 1/2/3/4/6/8 两轮交替，拟合出 first_pcm = 0.234 s + 74.6 ms/帧（残差 <21 ms）；斜率恰好等于 depth 单帧 31.7 ms 加 codec 单帧 40 ms。再用 --no-overlap 把并行项暴露：codec prime 0.230 s、backbone prefill 0.190 s，overlap 下取 max，所以固定项其实是 codec prime，不是 prefill。斜率/截距加隔离开关，比逐个埋点更省事。

Codec::restore_prime 按参考 codes 的最后 8 帧缓存 codec 递归状态，命中就跳过那 0.23 s。查出的问题是缓存条件错配：warmup 用的是 voice 0（官方样例），而 Web 默认 Serena，于是每个用户的第一次请求都在给用不到的音色付冷启动。部署层加一个 --voice serena 让默认音色对齐，首次 pcm 从 0.346 降到 0.280 s（wav 0.507→0.420），零引擎改动、稳态不退化。先查缓存命中条件，往往比写更快的 kernel 更划算。

那次优化留了个尾巴：prime 缓存是单条目，换音色立即失效（切回仍要 0.49 s）。下一节把这条最后的冷启动路径关掉，并顺带说明一个极易算错的账：被跳过的操作值 0.23 s，实际能省下的只有约 0.04 s。命中路径仍要发送 32 行共享 prefix——实测只值 2–4 ms（Ch 12.4），协议改动已判死；--first 2 --chunk 4 已是最优，别再试更小的首块。

Q8　某候选把 RTF 从 0.700 降到 0.666，能上线吗？
不能只看这个数。本例中帧数 69→76，音频 5.32→5.88 s，墙钟 3.724→3.914 s（+5.1%），RTF 下降纯粹因为分母变长。而且四条文本/seed 的 codes 与 WAV 全部不一致，已经不是同一个任务。正确顺序：先看过没过等价性门禁（逐字节 → ASR → 盲听），再看 elapsed_s 与每帧成本，最后才算 RTF。这个候选是 §17 的 flash-f32，结论是判死。
Q9　把首块从 2 帧减到 1 帧，首包为什么反而从 0.398 s 涨到 0.616 s？
因为 kTail = 2400 个样本大于单帧 kHop = 1920：第一个 chunk 的输出被全部留作 overlap tail，drop = 0，根本没有 PCM 写出。首包只能等第二个 chunk（4 帧），等于等 5 帧——0.234 + 5 × 0.0746 = 0.607 s，与实测 0.616 s 吻合。减小批次不一定降低延迟，要先看输出阈值。另外把 prime 的输出接进 tail 虽然能让 1 帧发出声音，但会把参考音色原声混进开头，不能这么修。

11.6 案例：把单条目缓存换成 LRU，以及「跳过 ≠ 省下」

§19 留下的冷启动尾巴，改法只有约 25 行：把 prime_codes_ / prime_inputs_ / prime_offset_ 换成 vector<PrimeEntry>，命中移到 front、新条目插 front、超出容量裁尾。关键是 key 取「真正决定状态的最小输入」——这里就是参考 codes 的最后 8 帧，而不是音色名字或索引。于是换文本不失效、同名不同内容不误命中，浏览器内联的临时音色（请求里带 codes）也自动纳入同一缓存。容量 4、每条目 1.04 MB，约 4.4 MB 上限；M5_PRIME_CACHE=1 复现旧行为、=0 禁用缓存，M5_PRIME_STATS=1 打印 hit/miss/save。

怎么验收：容量按 0,1,4,4,1,0 交替重启 server，每轮固定序列「serena → 官方样例 → serena → 官方样例 → serena → pcm」，共 36 次请求。服务端日志给出的 prime 调用统计是 0/13、8/13、11/13 次命中：容量 4 多出的 3 次正好是三个「切回音色」请求。切回三请求首包中位数 0.500 → 0.463 s（-7.5%）；用永远冷的 cap=0 轮做热漂移基线（s1→s3 +0.032 s）校正后，单条目的冷启动惩罚 +0.044 s 被压到 +0.005 s。更硬的门禁是 30 份 WAV 跨容量、跨冷热、跨 6 次重启全部同一哈希；用 6 个不同的内联临时音色逼出 LRU 驱逐，被驱逐后重算的两个音色哈希也与首次完全相同。

Key 取最小决定输入

prime 状态是 8 帧 codes 的纯函数，就别用音色名字当 key。缓存语义由被缓存的计算决定，不由请求身份决定。

先让缓存可观测

hit/miss/save 日志比「首包看起来快了」可靠得多；它还能给出每条目字节数，让容量选择有依据。

禁用缓存一物两用

cap=0 既是「命中省多少」的冷基线，又是同轮热漂移的校正量——不必另跑一轮漂移实验。

等价性跨命中状态

不只验证「同配置两次一样」，要覆盖冷、热、驱逐后重算、不同容量、不同进程；否则缓存可能悄悄改变输出。

Q10　缓存命中跳过了一个 0.23 s 的操作，首包为什么只快了约 0.04 s？
因为 prime 与 backbone prefill 并行：冷启动固定项是 max(0.230, 0.190) = 0.234 s，命中后 prime 消失，固定项退化成 prefill 的 0.190 s，省下的只是两者差值约 0.044 s（pcm 路径实测 0.058 s）。稳态章节里 max(depth, codec) 让「codec 单独 -33%」收益为零，是同一个结构在首包维度的翻版。算收益要重画并行结构，不能拿组件耗时直接相减；同理，也不要因为收益比预估小就判定优化无效——它仍然消除了换音色时用户能感知的那一次卡顿。

余量重估：串行项与 max() 的另一面

第 11 章教会你「非瓶颈分支的收益恒为 0」。但这句话有个前提：你要先知道哪个分支在瓶颈上。基线一旦改变（这里是把 depth 的 KV 读取范围从 256 缩到 32、又把 prime 缓存换成 LRU），瓶颈就换人了，昨天的结论今天就过期。这一章讲的是转正之后必须做的第二件事：重算收益矩阵，并用最便宜的手段验证它。

本章三个实验都在「不改模型图、不重训」的前提下完成，结果是一正两负。价值不在那个正的 2.3%，而在两次负结果各自留下的可复用判据。

12.1 先分清三个「推理时间」

问「还有没有优化空间」之前，必须先定口径。这三条账的分子分母都不同，混着谈会得出互相矛盾的结论：

口径当前值主导项约束
稳态墙钟 / RTF（69 帧长句）3.70 s / 0.694max(depth, codec)并行天花板，单侧优化归零
首包（pcm，命中）0.28 s固定 0.190 + 2 帧 × 74.6 ms不受 max() 约束
短句 RTF（≤7 字）常 >0.9固定项摊不薄与长句不是同一张账

稳态那条账的残酷之处在于两条轨道几乎完美平衡（2.853 vs 2.820，差 1.15%）。这是最坏的优化局面：你花力气把 depth 降 20%，codec 立刻变成新瓶颈，墙钟几乎不动。反过来，只要有一项不在 max() 里，它就值得优先动手。

12.2 串行项：唯一能 100% 兑现的那 0.677 s

backbone_s 在公式里是加法项，占墙钟约 18%。它不在瓶颈上，所以「降 10% 得 10%」在这里成立——这是全流程唯一还有这种性质的计算项。剩下的候选手段只有两类：

  1. KV 读取宽度（pad）：零重编译、开关现成，门禁是逐字节等价，成本最低。
  2. 中间档量化 / 分层混合精度：Q6_K、Q5_K 或前后层保 Q8，在 Q8 与 Q4 之间找音质拐点；一次把 Q4 试过头导致音频短 16%、韵律漂移被否掉，所以必须盲听。

先做第 1 项。历史上 backbone 的 pad 被硬编码成 256，原因很朴素——当初做 depth KV32 实验时要求「其他条件严格不变」。于是这个开关从没被单独测过。命令行的 --backbone 参数会整体替换 stage 启动命令，加个 M5_KV_PAD=128 前缀就能只注入 backbone 子进程（depth 仍是 32），一行代码都不用改。

12.3 「修好缺陷」不等于「拿到收益」

回到首包那条加法账。--first 1 一直有个众所周知的毛病：单帧 chunk 只有 1920 个样本，而 write_chunk 要把最后 kTail=2400 个样本留作下一块的 overlap 缓冲——全被扣住，一帧根本发不出声音，首包只能等第二个 chunk（共 5 帧，0.575 s）。

修法很直接：加一个 M5_FIRST_TAIL，让首个 emit chunk 少扣或不扣 tail。缺陷确实修好了，但收益是负的：

四个可迁移的点：

看斜率项归属哪一侧

首包 74.6 ms/帧 ≈ depth 31.7 + codec 40，是相加。改 --first 只动 depth 那一半，codec 的单帧调用固定开销却涨了——一侧省、另一侧还。

等价性可以比 SHA 更细

B 与 A 的 127,680 个样本只差 1 个样本、1 LSB、位于末尾（浮点求和顺序噪声），不是 chunk 边界伪影。codec 输出对 chunk 切分不敏感，此前担心的边界效应不存在。

纯调度实验是免费的对照

C 组（first 2 + 不扣 tail）逐字节一致，证明「边界移动本身零成本」；它把 B 的差异锁定在「少等一帧」这唯一变量上。

负结果要留复活条件

开关保留、默认关闭。复活条件：codec 单帧调用的固定开销显著下降（例如 codec 捆绑改造落地）后重测 --first 1 + M5_FIRST_TAIL=0。

12.4 先测占比，再谈改协议

prime 命中时可以跳过 codec prime，但引擎仍然把 32 行共享 prefix 发给 backbone stage——因为协议是「先发 header 再发两块矩阵」，少发一块需要改协议。省 64 KB 听起来值得改，先量一下：

sh=32 rs=71–85  hdr=0.1ms  shared=1.3–3.4ms  rest=7–12ms  wait=85–101ms  total≈105ms
m5-stage prefix hit sh=32 discard_ms=2.2–4.3

32 行（64 KB）的传输加丢弃只要 2–4 ms：占 prefill 往返（约 105 ms）的 3%，占命中首包（0.41 s）的 不到 1%。大头是 wait 段，也就是 backbone 对 rest 行做的真实 decode——那是算力，不是搬运。

算一下风险收益：省 2–4 ms，换一次管道错位崩溃的可能（这条协议以前踩过，错配时 stage 会读垃圾 header）。不成比例，直接判死。更重要的是它留下一条判据：凡是「优化传输」的提案，先问它在端到端里占几个百分点；单看「省了一半数据量」没有意义。

12.6 方法论补充

  1. 转正后立刻重算矩阵：KV32 转正让 depth 不再是瓶颈，「间接加速 depth」的历史收益（Q4 曾 −18%）换基线后只剩 −4.6%。旧数字必须带上它的基线。
  2. 在等价收益里挑最保守的配置：pad 32/64/128 差异在噪声内时选 128，因为它图重建次数减半，长句更稳。
  3. append 模式的 dump 是 A/B 地雷：--dump-codes 用追加写，冒烟轮与正式轮共用同名 tag 会静默叠加，产出假性 SHA 不一致（WAV 是截断写，不受影响，且 sha256sum 输出里 wav 在前）。A/B 脚本每轮先 rm -rf 结果目录，冒烟用独立 tag。
  4. 测量类实验别改会崩的代码：分段计时加一次对照就能定案，不必为 2–4 ms 去动协议。
  5. 先做零成本的那一个：本章第一项零重编译、门禁现成，跑 16 次就拿到 −2.3%；另外两项各花了半天证明不该做——判死也是产出。
Q11　backbone 只占墙钟 18%，为什么优化它比优化占 77% 的 depth+codec 更划算？
因为它们在墙钟公式里的位置不同。depth 与 codec 并行，墙钟取 max(2.853, 2.820)，两者只差 1.15%——把其中一侧降 20%，另一侧立刻成为新瓶颈，端到端收益约 0。backbone 是加法项：wall = backbone + max(...) + 固定，它降 7.7%，墙钟就真降约 7.7% 的那一份（实测 −2.3% 墙钟，符合 18% × 7.7% 量级）。判断优化价值不是看谁耗时最长，而是看它在公式里能不能兑现。这也解释了为什么「先降 depth」在 KV32 之前是对的、之后就不再是。
Q12　`--first 1` 从「等 5 帧」修成「1 帧就出声」，为什么首包仍不如 `--first 2`？
因为首包的成本是 depth 与 codec 相加而不是取 max（流水线还没填满）。--first 1 让 depth 少跑一帧（约 −31.7 ms，加上后续调度约 −75 ms），但 codec 要为一个 chunk 单独调用一次，单帧调用的固定开销让 codec_s 从 2.77 涨到 2.87 s，多花约 80 ms，两者抵消。实测 0.401 vs 0.387 s。要让它转正，得先把 codec 的单次调用开销降下来——所以这个开关的价值不是「现在能用」，而是把复活条件写清楚，等 codec 捆绑改造落地后只需重跑一次。
