# M5-TTS 端侧推理实战（二）：给一次语音请求做性能剖析

RTF 等于生成墙钟除以输出音频时长。一次 Flash Attention 对照里，墙钟从 3.724 s 升到 3.914 s，音频却从 5.32 s 变成 5.88 s，导致 RTF 表面改善。对于导航播报，响应时间、语速和文本都需要单独核对。

## 两层测量

1. 从请求边界记录墙钟、首包和帧数，固定文本、音色、seed 与分块配置。在线服务与 CLI 的参数都要记录。
2. 从流水线内部记录 backbone、depth 和 codec 耗时。并行阶段要找关键路径，分项之和可以大于墙钟。
3. 用同轮交替 A/B 估计变化。输出若有偏差，同时检查码本、转写和试听结果。

## 先估算值不值得做

depth 微基准对不同批量拟合出约 1.25 ms 的提交固定开销和约 0.91 ms 的每行开销。它解释了合批的吸引力，但每一步都需要上一索引。把条件输入清零的消融造成约 99.6% 的码本翻转，这条低成本实验把建模约束和后端提交成本区分开了。
